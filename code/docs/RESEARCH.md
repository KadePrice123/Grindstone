## Alpaca APIs (trading, data, news)

Alpaca's APIs (verified against docs.alpaca.markets, alpaca.markets/data, PyPI, and GitHub as of 2026-08-01) fully cover the platform's needs for equities, options (including multi-leg spreads via the 'mleg' order class at options Level 3), and spot crypto, with paper trading at paper-api.alpaca.markets and live at api.alpaca.markets. Market data comes in two retail tiers — Free (IEX stocks, indicative options quotes, 200 req/min, 30 websocket symbols, 15-min-delayed recent SIP history) and Algo Trader Plus $99/mo (full SIP, real-time OPRA options, 10,000 req/min per docs, unlimited websocket symbols). The News API (Benzinga-sourced, back to 2015) has REST and websocket streams and is included. The official alpaca-py SDK (v0.43.5, 2026-07-02) is actively maintained and covers trading, all market data, news, and streaming. Traditional futures are not offered; crypto perpetual futures exist only as a beta API surface not available to US customers.

**Recommendation:** Build the Alpaca integration on alpaca-py (pin >=0.43.x, Python 3.10+) with paper-api.alpaca.markets as the default environment and a config switch to live. Architect the order layer around Alpaca's real capability matrix: full order-type/bracket/OCO support for equities only; options limited to L1-L3 with mleg (max ~4 covered legs, limit/day, no bracket); crypto limited to market/limit/stop_limit with gtc/ioc. Ship on the free data tier (IEX + indicative options + crypto + news) and make Algo Trader Plus ($99/mo, SIP + OPRA) an optional user upgrade — the platform should detect entitlement at runtime via the feed parameter rather than hardcoding a feed. Use the trade_updates websocket for order-state UI, the v1beta1/news stream for an AI-news pane (Benzinga content includes full HTML and images, good for the browser-style UI), and budget for the hard 200 req/min trading rate limit with client-side throttling/queueing. Do not plan any futures features around Alpaca, and treat options history as starting Feb 2024 for any backtest/analytics features.

Key facts:
- TRADING HOSTS: live = https://api.alpaca.markets/v2, paper = https://paper-api.alpaca.markets/v2 (paper accounts default $100k, are created/deleted rather than reset, and simulate fills against real-time quotes with random 10% partial fills; paper uses IEX data). Auth via APCA-API-KEY-ID / APCA-API-SECRET-KEY headers.
- TRADING API RATE LIMIT: 200 requests/min per account across all trading endpoints; HTTP 429 on exceed; increases only via support request (per alpaca.markets/support/usage-limit-api-calls and community forum).
- ASSET CLASSES TRADABLE: US equities/ETFs (fractional to $1, market orders only for fractionals; short selling; 4x intraday / 2x overnight margin), US equity options, spot crypto (20+ coins, fractionable to 9 decimals, USD/USDC/USDT/BTC pairs). NO traditional futures (equity index, commodity). Crypto perpetual futures: beta API surface exists (Crypto Perpetuals Account Vitals endpoint; market data at https://data.alpaca.markets/v1beta1/crypto-perps/{loc}/...) but perps trading is not offered to US customers — treat as unavailable for this platform.
- OPTIONS LEVELS via API: Level 0 disabled; L1 covered calls + cash-secured puts; L2 adds long calls/puts; L3 adds spreads/multi-leg. No Level 4 (naked short options) — every short leg must be covered within the order. Options enabled by default in paper; live requires an approval flow.
- MULTI-LEG OPTIONS ORDERS: order_class='mleg' with a legs[] array; per-leg fields symbol, side (buy/sell), ratio_qty (must be in GCD-reduced form), position_intent (buy_to_open/sell_to_open/buy_to_close/sell_to_close). Docs demonstrate 4-leg structures (iron condors). Limit + day orders demonstrated for mleg; stop and stop_limit are restricted to single-leg options orders. No mixed equity+option legs; rolling short contracts in one order currently unsupported. Margin uses a 'universal spread rule' (piecewise max-loss), typically lower than per-spread margining. Early exercise via POST /v2/positions/{symbol_or_contract_id}/exercise; ITM by >=$0.01 auto-exercised at expiry, auto-liquidation within 1 hour before expiry if insufficient buying power.
- ORDER TYPES (equities): market, limit, stop, stop_limit, trailing_stop (amount or percent), plus auction orders MOO/LOO/MOC/LOC. TIF: day, gtc (90-day auto-cancel), opg, cls, ioc, fok. Order classes: simple, bracket (OTOCO), oco, oto. Extended hours 4:00-9:30am, 4:00-8:00pm, and overnight 8:00pm-4:00am ET with limit+day/gtc orders and extended_hours=true. CRYPTO: market/limit/stop_limit only, TIF gtc/ioc only — no bracket/OCO for crypto.
- TRADE UPDATES WEBSOCKET: wss://api.alpaca.markets/stream (live) and wss://paper-api.alpaca.markets/stream (paper); auth message then listen on 'trade_updates'; events: new, fill, partial_fill, canceled, expired, done_for_day, replaced, plus accepted/rejected/pending_*/stopped/calculated/suspended/order_replace_rejected/order_cancel_rejected. Paper endpoint sends binary frames (SDK handles this).
- MARKET DATA HOSTS: REST https://data.alpaca.markets (stocks v2/stocks/..., options v1beta1, crypto v1beta3, news v1beta1); streaming wss://stream.data.alpaca.markets/{version}/{feed}; sandbox mirrors at stream.data.sandbox.alpaca.markets; permanent test stream wss://stream.data.alpaca.markets/v2/test (symbol FAKEPACA).
- MARKET DATA TIERS: Free $0 — IEX-only real-time stocks (~2.5% of volume), indicative options quotes, crypto included, 200 API calls/min, 30 websocket symbols, historical queries within the last 15 minutes blocked for SIP data. Algo Trader Plus $99/mo — full SIP (all US exchanges, CTA+UTP), real-time OPRA options feed, 10,000 req/min (docs; marketing page says 'unlimited'), unlimited websocket symbols, no 15-min restriction. Most subscriptions allow only 1 concurrent websocket connection per endpoint (error 406 beyond).
- STOCK DATA: feeds iex, sip, boats (Blue Ocean ATS overnight), overnight (cheaper 15-min-delayed overnight derived from quotes); historical bars/trades/quotes/snapshots/auctions since 2016 (~7+ years marketed). Streaming channels: trades, quotes, bars, updatedBars, dailyBars, statuses, lulds, corrections, cancelErrors.
- OPTIONS DATA: historical only since February 2024 (bars/trades/quotes/snapshots/chain under data.alpaca.markets v1beta1); real-time streaming at wss://stream.data.alpaca.markets/v1beta1/{indicative|opra} with trades and quotes channels only (no bars, no greeks on the stream); wildcard '*' subscription prohibited for option quotes. Indicative feed = derived quotes + 15-min-delayed trades (free); OPRA = consolidated NBBO (paid).
- CRYPTO DATA: no auth required for historical crypto endpoints; streaming wss://stream.data.alpaca.markets/v1beta3/crypto/{loc} with loc = us, us-1 (Kraken US), eu-1 (Kraken EU); channels: trades, quotes, minute bars, daily bars, updated bars, orderbooks.
- NEWS API: REST GET https://data.alpaca.markets/v1beta1/news — params symbols, start, end, limit (1-50, default 10), sort, include_content, exclude_contentless, page_token; fields id, headline, author, created_at, updated_at, summary, content (HTML), url, images[] (thumb/small/large), symbols[], source. Source is Benzinga; history back to 2015; ~130+ articles/day; covers stock and crypto tickers. Real-time stream wss://stream.data.alpaca.markets/v1beta1/news ('T':'n' messages; subscribe with {"action":"subscribe","news":["*"]}). Included with data plans (no separate news fee documented).
- SDK: alpaca-py v0.43.5 released 2026-07-02 (PyPI), Apache-2.0, actively maintained (947 commits, 1.4k stars, 77 open issues), pydantic-based request/response models; covers Trading, Market Data (stocks/options/crypto/news), Broker API, and all websocket streams. GitHub states Python 3.10+ for current versions. Alpaca also ships an official MCP server (github.com/alpacahq/alpaca-mcp-server) exposing trading + data to LLM tools — directly relevant to the platform's MCP plans.
- DOCS DISCOVERY: the docs site moved under docs.alpaca.markets/us/; a machine-readable index of every page exists at https://docs.alpaca.markets/us/llms.txt (old /docs/* URLs partially 404).

Risks / constraints:
- Trading API is capped at 200 requests/min per account with no self-serve increase — a multi-tab dashboard polling positions/orders must multiplex through one shared client and rely on websockets, or it will 429.
- Free-tier data constraints leak into UX: IEX covers ~2.5% of volume (quotes can look stale/wrong vs other platforms), options quotes are indicative (not real OPRA NBBO) with 15-min-delayed trades, and recent-15-minute SIP history is blocked — mid-price fill logic (Kade's standing mid-fill rule) computed from indicative options quotes will diverge from live OPRA mids.
- No naked short options at any API level and no rolling of short contracts in a single mleg order — strategies like the condor/put-roller book must roll as two orders, briefly holding double margin or naked exposure risk in sequencing.
- Bracket/OCO order classes are not available for options or crypto; the platform's UI must gate those controls per asset class or orders will be rejected.
- Options historical data only reaches back to February 2024 — insufficient for long backtests; the existing data vault remains the deep-history source.
- Websocket connection limit is 1 per data endpoint per subscription (406 beyond) — the desktop app's multiple OS windows/tabs must share a single streaming connection through the Python backend, not open one per tab.
- No futures at all, and crypto perpetuals are beta/non-US only despite API surface existing — do not surface these in requirements; docs pages also conflict (marketing says 'unlimited' API calls on Algo Trader Plus, docs say 10,000/min; PyPI metadata says Python >=3.8 while GitHub says 3.10+), so pin against tested behavior.
- Paper trading fills are optimistic simulations (no market impact, latency, queue position, or regulatory fees; 10% random partial fills; IEX quotes) — paper P&L will overstate live performance, which matters given Kade's skepticism of good-looking numbers.
- GTC orders auto-cancel after 90 days; fractional equity trading is market-order-only — both need handling in order-management UI.
- Old docs URLs (docs.alpaca.markets/docs/...) are partially 404ing after the move to /us/ — any requirements doc should cite the /us/ paths and the llms.txt index to avoid dead links.

## TastyTrade Open API

TastyTrade's Open API is now OAuth2-only: legacy session-token auth was discontinued December 1, 2025, and every API user authenticates with 15-minute bearer access tokens minted from a never-expiring refresh token, which an individual can self-issue in minutes via a "personal OAuth grant" on my.tastytrade.com with no approval process. The API fully covers the platform's needs: equities, up-to-4-leg option orders, futures, futures options and crypto, a dry-run endpoint that returns buying-power effect, isolated margin requirement and itemized fees before submission, OTOCO/OTO/OCO complex orders, DXLink (dxFeed) streaming with Quote/Trade/Greeks/Candle events via a 24-hour api-quote-token, and an account-streamer websocket pushing full-object order/balance/position updates. A free sandbox (api.cert.tastyworks.com) supports OAuth2 and simulated fills but only 15-minute-delayed quotes. The de facto Python SDK is the unofficial MIT-licensed `tastytrade` package (tastyware), v13.2.2 released 2026-07-27, which wraps OAuth refresh, dry-runs, complex orders, DXLinkStreamer and the account streamer.

**Recommendation:** Build the TastyTrade integration on OAuth2 personal grants from day one: have Kade create a personal OAuth client (scopes read + trade) at my.tastytrade.com, store client_secret + refresh_token in the env/ secrets layout, and implement a token manager that mints 15-minute access tokens on demand and always sends a User-Agent header. Use the community `tastytrade` PyPI package (>=13.x, MIT, async, Python 3.11+) as the backend client rather than hand-rolling REST — it already handles auto-refresh, dry-runs, complex orders, DXLink and the account streamer, and pin it since it is unofficial and tracks a moving API. Make the dry-run endpoint a first-class platform feature (order preview screen showing buying-power impact, isolated margin requirement, and itemized fees — this is a differentiator vs Alpaca), drive all order/position/balance state from the account-streamer websocket (never poll /orders/live), and use DXLink Candle events for intraday charting plus Greeks events for live option analytics. Develop against the cert sandbox with a dedicated sandbox user, but plan production-account smoke tests early because sandbox quotes are 15-min delayed, fills are simulated by price rules, and market metrics/net-liq history don't exist there.

Key facts:
- AUTH: Session-token authentication was discontinued 2025-12-01 (announced by tastytrade email, tracked in tastyware/tastytrade issue #269). The official docs now state 'all tastytrade API users must use OAuth2 access tokens' — OAuth2 is mandatory, not optional.
- AUTH: Personal OAuth is self-service, no approval needed: my.tastytrade.com > Manage > My Profile > API > OAuth Applications > '+ New OAuth client' (scopes: read, trade, openid; client secret shown exactly once), then 'Manage > Create Grant' issues a refresh token directly — no authorization-code browser flow needed for your own account.
- AUTH: Access tokens come from POST https://api.tastyworks.com/oauth/token with grant_type=refresh_token + refresh_token + client_secret; access tokens last 15 minutes, refresh tokens never expire. Every OAuth request MUST send a User-Agent header in '<product>/<version>' format or it is rejected.
- AUTH: The authorization-code flow for connecting OTHER users' accounts requires becoming a verified 'trusted third party' (email api.support@tastytrade.com for review); until approved, an OAuth app can only access the owner's own account. tastytrade requires 2FA on the customer account for the sensitive read/trade scopes in that flow.
- SANDBOX: Full cert environment — REST at https://api.cert.tastyworks.com, account streamer at wss://streamer.cert.tastyworks.com, OAuth2 supported, separate sandbox user signup at developer.tastytrade.com/sandbox/. Resets every 24h (positions/trades wiped, users/accounts kept). Simulated fills: market orders fill at $1, limit <$3 fills instantly, limit >$3 stays Live forever. Quotes are always 15-min delayed; net-liq history and market metrics are unavailable in sandbox.
- TRADING: Instrument types = Equity, Equity Option, Future, Future Option, Cryptocurrency. Max legs: 4 for equity-option and future-option orders; 1 for equity, futures, and crypto orders. Order types: Limit, Market, Stop, Stop Limit, Notional Market (fractional/dollar-based, single leg, crypto + is-fractional-quantity-eligible equities). TIF: Day, GTC, GTD (gtc-date), plus equities-only Ext, GTC Ext, Ext Overnight, GTC Ext Overnight (24-hour session 7pm-7pm CT).
- DRY RUN: POST /accounts/{account_number}/orders/dry-run validates the order (symbol validity, expired options, conflicting orders, account standing) WITHOUT sending it and returns warnings[], buying-power-effect (change-in-margin-requirement, change-in-buying-power, current/new-buying-power, isolated-order-margin-requirement, is-spread, impact, effect) and fee-calculation (regulatory-fees, clearing-fees, commission, proprietary-index-option-fees, total-fees). The identical JSON is then POSTed to /accounts/{account_number}/orders to submit — ideal for an order-confirmation screen.
- ORDER MGMT: GET /accounts/{n}/orders (search, paginated), GET /accounts/{n}/orders/live (today's + still-working orders; docs explicitly warn NOT to poll it — use the account streamer or risk throttling/suspension), DELETE /accounts/{n}/orders/{id} (cancel -> 'Cancel Requested' status), PUT /accounts/{n}/orders/{id} (cancel/replace; only price, order-type, time-in-force may change). Complex orders: POST/GET/DELETE /accounts/{n}/complex-orders supporting OTOCO (trigger + profit + stop), OTO (trigger + up to 3 orders), OCO (2 closing orders); responses include buying-power-effect and fee-calculation too.
- MARKET DATA: GET /api-quote-tokens returns a customer-scoped DXLink token + dxlink-url; tokens valid 24 hours. Requires a real tastytrade CUSTOMER (opened account) — username-only registrations get quote_streamer.customer_not_found_error. DXLink websocket protocol: SETUP -> AUTH -> CHANNEL_REQUEST -> FEED_SETUP (use COMPACT format; FULL is being turned off) -> FEED_SUBSCRIPTION -> KEEPALIVE every ~30s (60s timeout). Granted event types: Profile, Quote, Summary, Trade, Greeks, TimeAndSale — Greeks stream gives volatility/delta/gamma/theta/rho/vega per option symbol.
- MARKET DATA: Candle events double as historical data: subscribe with symbol like AAPL{=5m} + fromTime epoch; DXLink replays all candles from fromTime to now then keeps updating the live candle (last event is the live one) — this is the API's intraday history mechanism (no REST end-time; ~1min granularity practical for ~1 day back, 1d candles for 1yr+). Streamer symbols come from the streamer-symbol field on instruments endpoints (/instruments/futures, /instruments/equities/:symbol, /option-chains/:sym/nested, /futures-option-chains/:code/nested, /instruments/cryptocurrencies).
- OPTIONS CHAINS: GET /option-chains/{symbol}/nested (expirations -> strikes -> call/put symbols; recommended), /option-chains/{symbol}/compact, /option-chains/{symbol} (full instruments); futures options via GET /futures-option-chains/{product_code}/nested; futures via GET /instruments/futures (?product-code[]=ES filter) and /instruments/future-products.
- ACCOUNT STREAMING: One-directional 'Account Streamer' websocket — production wss://streamer.tastyworks.com, sandbox wss://streamer.cert.tastyworks.com. Auth by sending the OAuth access token as 'Bearer <token>' in the auth-token field of each message. Flow: connect message with account-number array subscribes to ALL account updates (orders, balances, positions); heartbeat every 2s-60s required. Also public-watchlists-subscribe and quote-alerts-subscribe actions. Messages are full-object JSON (type: Order/etc.), never diffs; multi-leg fills may arrive as a Filled message with one leg's fills first, followed by messages containing all legs' fill data.
- PYTHON SDK: `tastytrade` on PyPI (tastyware/tastytrade on GitHub) v13.2.2 released 2026-07-27, MIT license, Python >=3.11 (supports 3.11-3.14), async, 100% typed with Pydantic models, 95%+ test coverage, ~251 stars — explicitly UNOFFICIAL. Covers OAuth sessions (auto token refresh since v12.0.0), dry-run orders returning BuyingPowerEffect/FeeCalculation, complex orders (OTOCO/OCO/OTO), replace/delete orders, DXLinkStreamer (Quote, Greeks, Candle...), account streamer, instruments/chains, watchlists, sandbox via Session(is_test=True), plus a tastytrade-cli companion. Docs: tastyworks-api.readthedocs.io.
- OTHER SDKs: tastytrade maintains an official TypeScript/JS SDK (@tastytrade/api on npm) that integrates the DxLink JS SDK; dxFeed also ships DXLink SDKs for .NET, Swift, C/C++, Java, JS. There is a tastytrade-sdk-python under the official tastytrade GitHub org but the community tastyware package is the actively-released one (13.x in July 2026).
- AGREEMENT: No application/approval gate for personal API use — using the API constitutes agreement to the API Terms of Service (assets.tastyworks.com/production/documents/USA/open_api_terms_and_conditions.pdf). API support contact: api.support@tastytrade.com. Streaming quotes require being an actual (account-opened) tastytrade customer; third-party multi-user apps require the trusted-third-party review.

Risks / constraints:
- The tastytrade Python SDK is unofficial (tastyware) with an explicit no-warranty disclaimer and effectively one primary maintainer; the API itself is versionless-URL and has changed behavior before (session-token removal with ~months of notice), so pin SDK versions and abstract the broker layer.
- Access tokens last only 15 minutes and every OAuth request without a properly formatted User-Agent header is rejected — token refresh must be built into the platform's request path, not done manually.
- The client secret is shown exactly once at app creation and regenerating it invalidates all active grants; losing/rotating it forces re-creating grants (operational runbook needed for secret rotation).
- Streaming quotes require a real, opened tastytrade customer account (Kade has one, but sandbox-only developers cannot get production quote tokens), and the api-quote-token expires every 24 hours so the streamer needs daily token renewal logic.
- Sandbox fidelity is limited: 15-minute delayed quotes, rule-based simulated fills (market fills at $1), 24-hour resets, occasional 422s on valid symbols, and no market metrics or net-liq history — final verification must happen against the live environment.
- Polling GET /orders/live is explicitly warned against and can lead to throttling or suspension of API access; the account streamer is mandatory for real-time order state.
- Market data entitlement is personal: the DXLink token identifies the individual customer, and redistributing data or serving other users would require the trusted-third-party review plus likely exchange-data agreements — fine for Kade's own desktop app, a blocker for any multi-user SaaS pivot.
- Historical data via Candle events has no end-time parameter and can flood the client (12 months of 1-minute candles is ~500k events); the platform needs interval-laddering logic, and there is no deep REST OHLC history endpoint on this API — plan to source bulk history elsewhere (e.g., Alpaca).
- Multi-leg option orders cap at 4 legs and equities/futures/crypto orders at 1 leg; cancel/replace can only change price, order-type, and time-in-force, so leg edits require cancel + resubmit.
- Complex (OTOCO/OTO/OCO) orders use separate endpoints and IDs from regular orders — order-management UI must track complex-order-id vs nested order ids or cancels will target the wrong object.

## Webull & Fidelity reality check

Webull is genuinely integrable: the official Webull OpenAPI (developer.webull.com) is open to US retail individual account holders with a $100 minimum net account value, a 1-2 business-day application review, and supports live trading of stocks/options/futures/crypto plus market data and a sandbox — making the old unofficial 'webull' pip package (last released Jan 2023, login currently broken via 403, ToS-risky) obsolete. Fidelity is the opposite: there is no official public retail trading API in any form as of 2026, aggregators that can reach Fidelity (SnapTrade via OAuth, Akoya-based feeds) are strictly read-only, Plaid cannot reach Fidelity at all, and screen-scraping (Playwright/Selenium projects) violates ToS against a broker that actively blocks scrapers. The requirements doc should promise Webull trading via the official API and, at most, read-only Fidelity portfolio display — never Fidelity order execution.

**Recommendation:** Tier the broker integrations in the requirements doc. Tier 1 (full trading, day one): Alpaca and TastyTrade via their official APIs with the user's existing keys. Tier 2 (full trading, requires user action): Webull via the official Webull OpenAPI Python SDK — the user must apply in the Webull portal ($100 minimum account value, 1-2 day discretionary review); build against the auto-approved sandbox immediately and design the credential layer to tolerate short-lived keys until the 1-day/7-day key-validity question is resolved empirically. Explicitly do NOT build on the unofficial 'webull' pip package — it is stale, currently login-broken, and superseded. Tier 3 (read-only or absent): Fidelity — state plainly in the doc that retail trade execution at Fidelity is impossible through any legitimate channel in 2026; the only honest options are (a) read-only portfolio/balances display via SnapTrade's OAuth-based Fidelity integration, (b) manual CSV import from Fidelity exports, or (c) omission. Reject screen-scraping approaches (Playwright/Selenium) as a supported feature: they violate Fidelity's ToS, break without notice, and Fidelity actively counters them — at most note them as unsupported user-side hacks outside the product boundary.

Key facts:
- Webull OpenAPI is officially available to US retail individuals: 'Retail Individual Mode' is 'Applicable to direct account holders' trading their own accounts (developer.webull.com/apis/docs/authentication/IndividualApplicationAPI).
- Webull OpenAPI eligibility per Webull help center: an active Webull brokerage account with 'a minimum net account value of $100'; applications are 'reviewed based on your risk profile and trading history'; review takes 1-2 business days (webull.com/help/faq/10512).
- Webull OpenAPI supports stocks, options, futures, crypto, and event contracts; order place/modify/cancel including fractional shares; options use the same order endpoint with instrument_type: OPTION and a legs array (developer.webull.com/apis/docs/trade-api/options/).
- Webull OpenAPI transport/SDKs: REST (HTTP), MQTT for real-time market-data streaming, gRPC for order-event streaming; official Python SDK supports Python 3.8-3.13 (github.com/webull-inc/openapi-python-sdk); Java SDK JDK 8+.
- Webull OpenAPI has a sandbox: separate sandbox application with automatic approval 'within a few minutes', shared test accounts usable immediately, endpoint events-api.sandbox.webull.com — this is a test environment, not Webull's in-app paper trading.
- Webull OpenAPI pricing: no extra charge for API access, trading fees identical to the app; real-time market data subscriptions are purchased separately (developer.webull.com/apis/docs/faq/).
- Webull help center states generated API keys have 'a default validity period of 1 day' and a maximum of 7 days, with at most 3 key generations/resets per day — while the developer-portal docs describe App Key/Secret reset 'anytime' with no expiry mentioned; this conflict must be verified empirically during onboarding because a 7-day key ceiling would force weekly re-provisioning.
- Unofficial 'webull' pip package (tedchou12/webull): last PyPI release 0.6.1 on 2023-01-10; login requires harvesting a 'did' token from a real browser session due to Webull image verification; issue #456 (opened 2025-09-15, still open) reports wb.login() returning HTTP 403 with a non-JSON body; 81 open issues; README disclaims 'not extensively tested, use at your own risk'.
- Fidelity offers NO official public trading API for retail customers as of 2026 — confirmed by TradersPost's article (updated 2026-07-31): institutional-only FIX connectivity exists with minimums 'in the millions' and certification requirements.
- Fidelity's retail platforms (Active Trader Pro; the new Fidelity Trader+ launched Sept 2025) expose no automation interface or API.
- Fidelity actively blocked screen-scraping in Oct 2023, cutting off aggregators that would not move to its sanctioned Akoya feed (riabiz.com); Plaid refused Akoya and consequently offers NO Fidelity connection at all — still unresolved per Nov 2025 RIABiz reporting.

SnapTrade does support trading at other brokers and announced a Webull API partnership in Dec 2025.
- Akoya (the Fidelity-sanctioned data network) is B2B only — vetted fintech data recipients under contract, not individual developers — and provides read-only account/investment/transaction data; its 'Payments' product is payment enablement, not brokerage order execution.
- Unofficial Fidelity automation exists only as browser puppeteering: kennyboy106/fidelity-api (Playwright, handles 2FA), Jeebus678/FidelityAutobot (Selenium), fidelipy — all unofficial, ToS-violating, and brittle against a broker with a demonstrated history of hunting scrapers.
- SnapTrade itself is a B2B API platform (app developers register for API keys; per-connection pricing) — feasible for this project as the one legitimate route to displaying Fidelity holdings, but it adds a third-party dependency and cost.

Risks / constraints:
- Webull key-lifetime ambiguity: Webull's help center says generated API keys default to 1-day validity (max 7 days, max 3 resets/day), while developer docs imply non-expiring App Key/Secret — if the help center is right, unattended long-running trading needs an automated re-provisioning story or the integration degrades weekly.
- Webull API approval is discretionary ('reviewed based on your risk profile and trading history') — access is not guaranteed and could presumably be revoked; the requirements doc cannot treat Webull as unconditionally available.
- Webull real-time market data via OpenAPI costs extra (separate subscriptions), so quote display for Webull is a paid dependency, unlike Alpaca/TastyTrade data already in hand.
- The unofficial 'webull' package is a trap: currently failing logins (403, issue #456 open since Sep 2025), 2.5+ years since a PyPI release, requires browser-token extraction, and using it risks account restriction — any requirement written against it will not survive contact.
- Fidelity trading automation is impossible for retail, full stop — any stakeholder expectation of 'Fidelity order entry' must be killed in the requirements doc; TradersPost-style 'automation' marketing for Fidelity does not include direct API order execution.
- Fidelity read-only via SnapTrade means a B2B relationship with SnapTrade (developer registration, per-connection pricing, their uptime and their Fidelity relationship) — a third-party single point of failure for that feature; Plaid is a dead end for Fidelity and Akoya will not contract with an individual.
- Screen-scraping Fidelity (fidelity-api/FidelityAutobot/fidelipy) violates Fidelity's ToS at a firm with a demonstrated enforcement posture (2023 aggregator cutoff); shipping it in a product invites account bans and breakage on every UI change.
- Webull OpenAPI sandbox uses shared test accounts — fine for API-shape development, but not a faithful paper-trading simulation of fills; strategy validation still belongs on Alpaca paper accounts.
- Open-banking/data-access economics are shifting (JPMorgan/Fidelity/Schwab pushing fees onto aggregators per Nov 2025 RIABiz) — aggregator-based read-only Fidelity access could get more expensive or narrower over the product's life.

## Desktop shell technology (tab tear-off requirement)

Across the six candidate shells, only two can genuinely deliver Chrome-style tab tear-off (live tab dragged out into a new OS window and regrouped between windows): Electron (via WebContentsView reparenting across BaseWindows — the same architecture class Chrome and VS Code use) and PySide6/Qt WebEngine (via Qt widget reparenting of QWebEngineView between QMainWindows). Tauri, pywebview, and Neutralino can each open new OS windows programmatically but cannot move a live webview between windows — a "torn-off" tab must be destroyed and re-created in the new window with serialized state — and CEF Python is effectively dead (no Python 3.12 support, no releases in years). Electron + a PyInstaller-packaged Python FastAPI sidecar, bundled with electron-builder into an NSIS/Squirrel Windows installer, is the recommended approach; its WebContentsView API also directly provides the "embed a real browser view" feature for the integrated-browser requirement.

**Recommendation:** Choose (a): Electron + Python sidecar. Concretely: Electron 43+ shell (BaseWindow + WebContentsView architecture, not legacy BrowserWindow-with-webview), React tab-strip UI in a chrome layer, one WebContentsView per tab, tear-off implemented as drag-out detection -> IPC -> new BaseWindow -> reparent the existing webContents into a new WebContentsView (live, no reload) — the same pattern class as Chrome/VS Code, and the only one that also gives the integrated real-browser tabs (WebContentsView pointed at arbitrary URLs) for free. Backend: FastAPI frozen with PyInstaller, spawned by Electron main as a child process, IPC over localhost HTTP + WebSocket; package both with electron-builder into an NSIS installer. Accept the ~150-250 MB installed footprint as the cost of the flagship UX requirement. Fallback if Electron is vetoed: PySide6/Qt WebEngine (6.11.x, LGPL) is the only other stack that can truly reparent live web views between windows, at the price of fragile WebEngine packaging and a lagging Chromium. Explicitly reject CEF Python (dead, no Python 3.12), Neutralino (process-per-window, no view transfer), and treat pywebview/Tauri as viable only if tab tear-off is downgraded to 'reopen tab in new window with state restore'.

Key facts:
- Electron: newest stable major is Electron 43, released 2026-06-30 (endoflife.date/electron); majors ship every 8 weeks and the latest 3 are supported. MIT licensed.
- Electron multi-window: unlimited BrowserWindow/BaseWindow instances created programmatically from the main process at any time, including at cursor position on a drag-end gesture — this is exactly how VS Code's floating editor windows and Chromium-family apps do tear-off.
- Electron tab tear-off mechanics: HTML5 drag-and-drop is confined to one window, so the standard pattern is renderer detects drag-out -> IPC to main -> main creates a new window and REPARENTS the live view: a WebContentsView is removed from one BaseWindow.contentView and a new WebContentsView constructed with the existing `webContents` is added to another window via addChildView() — the page keeps running, no reload. A WebContents may only be presented in one WebContentsView at a time (electronjs.org/docs/latest/api/web-contents-view). Libraries like electron-tabs provide in-window drag/drop tab strips.
- Electron embedded real-browser feature: BrowserView is deprecated (since Electron 30 it is a shim over WebContentsView); the current API is WebContentsView + BaseWindow — view.webContents.loadURL(url), view.setBounds(...), multiple views per window for split layouts (electronjs.org/blog/migrate-to-webcontentsview). This is the correct primitive for both the app's own browser-style tabs and an integrated web-browser pane.
- Electron custom right-click menus: full support — intercept webContents 'context-menu' event, show native Menu.buildFromTemplate(...).popup() or a custom HTML menu; per-element menus are routine.
- Electron + Python IPC/packaging: the established sidecar pattern is PyInstaller-frozen FastAPI/Flask exe spawned as a child process, frontend talks HTTP/WebSocket on localhost; electron-builder bundles the PyInstaller dist into the installer (multiple maintained templates, e.g. shamsharoon/electron-fastapi-exe, gnoviawan/fast-api-electron-js). electron-builder produces NSIS installers on Windows.
- Electron size: hello-world distributable ~45-115 MB depending on optimization (electron-fiddle Windows installer measured 112 MB); installed footprint ~200 MB+, plus the PyInstaller sidecar (typically 30-150 MB depending on numpy/pandas payload).
- pywebview: v6.2.1 released 2026-04-15, actively maintained (BSD license); v6 added state management and network event handling. Multi-window supported via webview.create_window() including after start; frameless windows with pywebview-drag-region CSS class for custom title bars; IPC is the tightest of any option (Python IS the host process: js_api bindings, expose(), evaluate_js()). BUT: each window is an independent WebView2 instance — no API to move a live webview/DOM between OS windows, so tear-off requires destroy-and-recreate with serialized tab state; no cross-window drag-tracking API; no native context-menu API (HTML menus only). Packaging via PyInstaller is small (~30-60 MB) since it uses the OS-provided Edge WebView2 runtime.
- PySide6/Qt WebEngine: v6.11.1 released 2026-05-15; LGPLv3 (or GPL/commercial) — LGPL is workable for a packaged app if Qt libs remain replaceable (PyInstaller default dynamic linking satisfies this). Genuine tear-off is achievable: QWebEngineView is a QWidget and can be reparented between QMainWindows without reloading; QTabBar gives full drag detection; QDetachTabWidget and tabbed-browser examples (pythonguis.com) exist; createWindow() override handles popups. Custom context menus via contextMenuEvent are first-class. Downsides: PyInstaller + QtWebEngine packaging is a chronically fragile combination (file locations shift between releases — Qt forum threads through 2025-26 confirm), app size is large (QtWebEngine wheel payload pushes packaged apps to ~150-300 MB), and Chromium in Qt lags the real Chrome by several releases.
- CEF Python (cefpython3): effectively dead — no PyPI release in years, open issues requesting Python 3.12 support unanswered (github.com/cztomczak/cefpython/issues/673), Snyk classifies it as discontinued/low-maintenance. Kade's machine runs Python 3.12.10, so cefpython cannot even be installed there. Disqualified.
- Tauri: stable v2.10.1 as of March 2026 (MIT/Apache-2.0). Multi-window is supported (WebviewWindow created from JS or Rust), and spacedriveapp/drag-rs provides native drag-out with a Tauri v2 plugin. BUT official discussion (tauri-apps discussion #6464) confirms Tauri does not support multiple webviews per window on stable — the tab strip must be pure HTML — and a live webview cannot be moved between windows, so tear-off is destroy-and-recreate with state serialization. Python requires a sidecar (PyInstaller exe via shell plugin, e.g. dieharders/example-tauri-v2-python-server-sidecar) AND a Rust toolchain in the build. Tiny footprint: ~3-10 MB binary; WebView2 bootstrapper adds ~1.8 MB (offline installer +127 MB, fixed runtime +180 MB); NSIS and MSI installer targets built in.
- Neutralino: v6.4.0 current; multi-window works by spawning a separate OS process per window with communication over the storage API — no shared runtime, no view transfer, no native menus. Unsuitable for tab tear-off by architecture.
- Windows installer story ranking: Electron (electron-builder NSIS, auto-update ecosystem) and Tauri (NSIS/MSI built-in) are turnkey; PySide6 needs PyInstaller + separate installer tooling (Inno Setup/NSIS) and fights WebEngine packaging; pywebview is easy PyInstaller but same separate-installer work.
- Cross-window drag limitation is universal at the HTML level: HTML5 drag-and-drop cannot cross OS-window boundaries in ANY of these frameworks. Chrome-style behavior always requires native-side coordination (track cursor during drag, detect leaving the tab strip, create/target windows from the privileged process). Electron and Qt are the two frameworks where the privileged process can also carry the LIVE view across; the others can only fake it with reload.

Risks / constraints:
- Tab tear-off is nowhere a built-in API — even in Electron it is a custom implementation (drag tracking + IPC + WebContentsView reparenting). Budget real engineering time; electron-tabs handles only in-window dragging, not cross-window tear-off.
- Electron footprint and memory: ~112 MB hello-world installer, one Chromium per app plus a PyInstaller Python bundle; total installed size likely 250-400 MB with numpy/pandas in the backend.
- Sidecar lifecycle: the PyInstaller backend exe must be spawned, health-checked, port-collision-handled, and reliably killed on app exit (orphaned python.exe processes are the classic bug in this pattern); Windows Defender/SmartScreen may flag unsigned PyInstaller exes — code-signing needed for distribution.
- Electron majors ship every 8 weeks with only 3 supported — pin a version and plan periodic upgrades; BrowserView code samples found online are deprecated (shimmed since Electron 30), so build on WebContentsView from day one.
- A WebContents can only live in one WebContentsView at a time — the tear-off reparenting code must destroy/create views in the right order or tabs will white-screen; window-close must not auto-destroy webContents that were reparented (explicit ownership management required).
- If PySide6 is chosen instead: LGPLv3 compliance (keep Qt dynamically linked), PyInstaller+QtWebEngine breakage on version bumps, and Qt's Chromium lags real Chrome — a problem for an app whose UI imitates a browser and embeds live broker sites.
- Tauri's small size is tempting but its stable channel cannot put multiple webviews in one window and cannot move a webview between windows — Chrome-style tear-off would be a reload-based imitation; it also adds a Rust toolchain to a Python shop.
- OpenWebUI integration (separate research thread) will itself be a localhost web service — the Electron WebContentsView approach happens to make embedding it trivial, but any per-window-process framework (Neutralino) or single-webview framework (Tauri stable) makes multi-pane AI + trading layouts harder.

## Open WebUI (architecture, extension points, license)

Open WebUI (latest v0.11.0, released 2026-07-27) is a SvelteKit SPA served by a Python FastAPI backend with SQLAlchemy (SQLite default, Postgres supported), Socket.IO for realtime, and a pluggable RAG stack (ChromaDB default vector DB, sentence-transformers/all-MiniLM-L6-v2 default embeddings, 13 vector DB backends, 8 extraction engines). It is highly embeddable for this trading platform: trusted-header SSO can auto-login users from an outer app via a local reverse proxy, a full REST API (Bearer API key or JWT) manages files/knowledge/models/chats, native Anthropic support exists both as a provider connection and as an Anthropic-compatible v1/messages proxy, and native MCP (Streamable HTTP, admin-configured, OAuth 2.1) landed in v0.6.31 with mcpo as the proxy for stdio servers. The critical constraint is the license: since v0.6.6 (2025-04-19) the Open WebUI License is BSD-3 plus a branding-protection clause that forbids removing/obscuring "Open WebUI" branding unless the deployment has <=50 users in any rolling 30-day window, the deployer has written contributor permission, or an enterprise license is purchased — so a rebranded/refactored embed inside a distributed commercial product needs either the under-50-user posture (per deployment, fine for a personal desktop app) or an enterprise license.

**Recommendation:** Embed a stock (not forked) Open WebUI as a service inside the platform rather than refactoring its source: run it as a pip-installed FastAPI app on loopback, front it with the platform's own local proxy that injects WEBUI_AUTH_TRUSTED_EMAIL_HEADER for seamless auto-login into the tab/webview, drive dark/light by writing localStorage.theme='dark'|'light' into the webview before load, and integrate all trading features through the REST API (knowledge upload + /api/chat/completions) and the platform's own MCP server exposed over Streamable HTTP (registered admin-side in External Tools; wrap any stdio-only servers with mcpo). Connect Claude via the native Anthropic connection (https://api.anthropic.com/v1) — no pipe needed — and note that the Claude Code *subscription* cannot legally back OpenWebUI chat traffic (subscription terms cover Claude Code usage, not arbitrary API relays), so budget an Anthropic API key for OWUI chat. Licensing: for a personal/single-user desktop product each deployment is far under the 50-user/30-day threshold, so full rebranding of the embedded UI is permitted per the license's small-scale exemption; if the platform is ever distributed commercially at scale, either keep 'Open WebUI' branding visible or obtain an enterprise license — plan the UI so branding can be toggled back on. Build new AI logic as Functions (Pipe/Filter/Action) and OpenAPI/MCP tool servers, not Pipelines (now officially legacy).

Key facts:
- Current release: Open WebUI v0.11.0, released 2026-07-27 ("The Interface, Reorganized" — unified settings, rebuilt sidebar, remappable shortcuts); previous v0.10.2 on 2026-07-01.
- Architecture: SvelteKit SPA frontend (src/) compiled to static files and served by the same FastAPI process (backend/open_webui/); Python 3.11; SQLAlchemy 2.0 ORM with SQLite default (DATABASE_URL supports PostgreSQL/MySQL); Socket.IO (socket_app) for realtime streaming/events; optional Redis for sessions and horizontal scaling.
- RAG internals: default vector DB is ChromaDB (VECTOR_DB env var); factory supports 13 backends — Chroma, PGVector (both officially maintained), Milvus, Qdrant, Pinecone, S3Vector, OpenSearch, Elasticsearch, OpenGauss, MariaDB-Vector, Oracle23ai, Weaviate, Valkey. Default embedding: sentence-transformers/all-MiniLM-L6-v2 (local SentenceTransformers engine, 384-dim); RAG_EMBEDDING_ENGINE/RAG_EMBEDDING_MODEL switch to Ollama/OpenAI-compatible embeddings. 8 content-extraction engines: Tika, Docling, Azure, Mistral OCR, Datalab Marker, MinerU, PaddleOCR, custom. Hybrid retrieval = BM25 + vector search + cross-encoder reranking (ENABLE_RAG_HYBRID_SEARCH); Full Context mode bypasses chunking; agentic knowledge tools (query_knowledge_files, grep_knowledge_files, kb_exec with ENABLE_KB_EXEC=True).
- REST API (Bearer API key 'sk-...' from Settings>Account, or JWT; Swagger at /docs with ENV=dev): POST /api/chat/completions (OpenAI-compatible), POST /api/v1/files/ (upload), GET /api/v1/files/{id}/process/status, POST /api/v1/knowledge/{id}/file/add, POST /api/v1/retrieval/process/web, GET /api/models, /api/v1/models/create|import|export|sync, /ollama/* proxy. Routers also exist for chats.py, folders.py, notes.py, prompts.py, tools.py, functions.py, users.py, groups.py, channels.py, memories.py — programmatic chat/knowledge/model management is all HTTP.
- Extension points: (a) Functions — in-app Python plugins, type auto-detected from top-level class Pipe/Filter/Action/Event; Pipes create custom model providers, Filters hook inlet/stream/outlet, Actions add chat-message buttons with event-driven UI; installed per-instance via admin UI or community site. (b) Tools — Python tool plugins callable by models, plus user-addable external OpenAPI tool servers. (c) Pipelines — separate OpenAI-compatible server on port 9099; the docs now explicitly mark Pipelines as LEGACY: 'Pipelines are legacy and are no longer recommended' — use Functions and OpenAPI/MCP tool servers instead.
- Auth/auto-login: trusted-header SSO via WEBUI_AUTH_TRUSTED_EMAIL_HEADER (+ TRUSTED_NAME/GROUPS/ROLE headers) auto-registers and logs in the user for any request carrying the header — an outer desktop app can run a tiny local reverse proxy that injects the header, giving seamless embedded auto-login (must firewall OWUI to loopback; anyone who can send the header is any user). OAuth2/OIDC (Google/Microsoft/GitHub/generic OIDC, one OIDC provider at a time), OAUTH_AUTO_REDIRECT to skip the login screen, ENABLE_OAUTH_TOKEN_EXCHANGE to swap IdP tokens for OWUI JWTs. JWTs signed with WEBUI_SECRET_KEY; API keys usable on API endpoints (not the SPA). No documented iframe-embedding/postMessage login API.
- License: v0.6.6 (2025-04-19) onward is the 'Open WebUI License' = BSD-3-Clause + branding-protection clause: you may NOT alter, remove, or obscure 'Open WebUI' branding (name, logo, UI marks) in any deployment or distribution EXCEPT (1) <=50 users in any rolling 30-day period, (2) written permission as a substantive contributor, (3) paid enterprise license. Prohibits shrinking/relocating/recoloring the marks and equal-prominence co-branding; code through v0.6.5 remains plain BSD-3. Contributions require a CLA.
- Theming: theme is read from localStorage key 'theme' by an inline script in src/app.html before first paint; values: 'system', 'dark', 'light', 'oled-dark', 'her'; it toggles the 'dark' class on documentElement. NO URL parameter and no postMessage API — external control requires writing localStorage before load (possible from an embedding webview/Electron-style host or same-origin injection), not from a cross-origin iframe.
- Claude integration: (a) Native provider connection — Admin Settings > Connections with base URL https://api.anthropic.com/v1 (Anthropic's OpenAI-compatible endpoint); docs state no middleware/pipes needed; streaming, multi-turn, and tool calling work. (b) Native Anthropic v1/messages proxy (ENABLE_ANTHROPIC_API; PR #21534): OWUI exposes POST /api/v1/messages + count_tokens with x-api-key support, so Anthropic-native clients (including Claude Code) can point AT Open WebUI. (c) Community 'Anthropic manifold' pipe Functions remain available on openwebui.com/functions for finer control.
- MCP: native MCP support since v0.6.31, Streamable HTTP transport ONLY, configured admin-only under Admin Settings > External Tools; auth modes None/Bearer/OAuth 2.1 with PKCE + Dynamic Client Registration/OAuth 2.1 Static (added ~March 2026); custom headers support {{USER_ID}}/{{USER_EMAIL}}/{{USER_GROUPS}} templating. stdio/SSE MCP servers need mcpo (MCP-to-OpenAPI proxy, latest v0.0.20, 2026-02-27, auto-reconnect added) or any streamable-HTTP bridge.
- Open WebUI ships an official Electron-based desktop app (github.com/open-webui/desktop) — relevant precedent for packaging it inside a Windows executable.

Risks / constraints:
- License: the branding clause (v0.6.6+) binds any distribution — shipping a rebranded Open WebUI inside a commercial product is only safe while each deployment stays <=50 users per rolling 30-day window; 'commercial-looking' does not matter, user count and branding visibility do. Deep source refactoring is allowed by BSD-3 terms, but the branding must survive unless an exemption applies; enterprise license is the only clean path for a scaled white-label.
- The under-50-users exemption is measured per deployment in a 30-day window, but aggregate distribution of many single-user copies is legally untested wording — get written clarity from the maintainers before mass distribution of a rebranded build.
- Trusted-header SSO is a footgun: any process that can reach the OWUI port can authenticate as ANY user, admin included. The embedded instance must bind to 127.0.0.1 and only the injecting proxy may reach it; on a shared Windows box other local processes can still hit loopback ports.
- No supported iframe/postMessage login or theming API: cross-origin iframe embedding cannot set localStorage.theme or the auth token; the design must use a webview/same-origin proxy, and an OWUI upgrade could change the localStorage contract (it is an internal, undocumented mechanism).
- Deep refactoring creates a fork-maintenance treadmill: OWUI ships breaking releases fast (0.10 -> 0.11 reorganized the whole interface in July 2026), and the docs URL structure, API surfaces, and internal stores churn; integrate via API/reverse-proxy, not source edits, wherever possible.
- Native MCP is Streamable HTTP only and admin-configured — stdio MCP servers (the common Claude Code pattern) require running mcpo or an HTTP bridge as an extra child process; OAuth 2.1 MCP tools cannot be default tools (interactive browser flow).
- Pipelines are officially legacy — any requirements doc leaning on the Pipelines server (port 9099) is building on a deprecated component.
- Swagger /docs requires ENV=dev; some /api/v1/* routes (chats, folders, notes) are internal-facing and less stability-guaranteed than the documented files/knowledge/models endpoints — pin the OWUI version and regression-test API integrations on upgrade.
- Using a Claude Code subscription as the token source for OWUI chat traffic violates the subscription's intended use; the MCP-server-into-Claude-Code direction is fine, but OWUI-as-chat-frontend needs a metered Anthropic API key.
- SQLite default DB and local ChromaDB are single-node; fine for a desktop app, but file locking on OneDrive-synced folders can corrupt them — keep OWUI data dir out of synced paths.

## Claude / MCP / Agent SDK

Claude Agent SDK is a Python/TypeScript library for building desktop agents in your own process (not hosted). It requires an ANTHROPIC_API_KEY (API key auth, not OAuth), and uses MCP (Model Context Protocol spec 2026-07-28, Streamable HTTP transport) to pipe tools/resources bidirectionally. Subscription plans include optional Agent SDK credits ($20–$200/mo as of June 15, 2026), but the system was paused and currently "still draws from subscription usage limits." Third-party desktop apps must use API keys, not OAuth login. OpenWebUI can integrate Claude via explicit API key configuration. Vision/images are supported via content blocks in the SDK's streaming interface.

**Recommendation:** For a Python + React desktop trading platform with AI features: (1) **Agent SDK core**: Use Python Agent SDK library for the agentic loop — it's a proven harness with MCP, tools, permissions, sessions; run it in the Python backend process. (2) **MCP server for brokers**: Implement an MCP server (FastMCP v3.4.3) exposing Alpaca, TastyTrade, Webull, Fidelity APIs as MCP tools (order placement, quote fetch, position read) and resources (chart images, live positions). Transport via stdio (local Python subprocess) for latency-sensitive work. (3) **Images/context**: Desktop app captures chart screenshots and market data, passes to Agent SDK via streaming content blocks (images work out of the box in SDK's prompt parameter). Claude calls back to broker MCP tools to execute trades. (4) **OpenWebUI bridge** (optional): If you want OpenWebUI as an alternate UI, configure it with explicit ANTHROPIC_API_KEY pointing to your API account; it will work but does not auto-integrate MCP from your desktop app — you would need a separate OpenWebUI MCP server for brokers. (5) **Auth**: Use ANTHROPIC_API_KEY (environment variable or credential file); do NOT attempt OAuth/claude.ai login in third-party app — prohibited by ToS. (6) **Billing**: Choose between (a) subscription + paused credits (verify current status with Anthropic), or (b) explicit API key with per-token pay-as-you-go billing. For prototyping, use a subscription; for production, migrate to API key with cost tracking. (7) **Avoid**: Managed Agents (hosted-only, async-focused, wrong architecture); Tool Runner alone (no built-in tools, more boilerplate). Agent SDK is purpose-built for your use case.

Key facts:
- Claude Agent SDK ships as Python (`claude-agent-sdk`) and TypeScript (`@anthropic-ai/claude-agent-sdk`) libraries — runs the agentic loop in your own process on your own infrastructure (not Anthropic-hosted, unlike Managed Agents).

## Charting libraries

As of 2026-08, TradingView Lightweight Charts v5.2.0 (Apache-2.0) is the strongest free base for a professional trading chart: fastest and most mature canvas engine, native multi-series/multi-pane (multi-ticker overlay), built-in price lines and series markers (strike overlays), and a first-class plugin/primitives system — but it ships zero drawing tools and no indicator framework, so those are custom-build items. KLineCharts 10.0.1 (Apache-2.0) is the batteries-included alternative with 16 built-in drawing overlays (incl. Fibonacci and annotations) and a runtime custom-indicator API (registerIndicator), at the cost of weaker multi-ticker support and a smaller Western ecosystem. TradingView Advanced Charts is free-with-approval but its license (companies only, public-facing products, private repo, non-redistributable, TradingView compliance access) makes it unusable for a personal desktop executable; Highcharts Stock is ~$833/developer commercial; Chart.js's financial plugin is stagnant at 0.2.1. Recommended: Lightweight Charts v5 primary + ECharts 6 for payoff diagrams + Python-backend-computed user indicators.

**Recommendation:** Adopt TradingView Lightweight Charts v5.2.0 (Apache-2.0) as the primary price-chart engine, and treat these as explicit custom-build items in the requirements doc: (1) Drawing-tools layer — fork the MIT deepentropy/lightweight-charts-drawing plugin (68 tools incl. trendlines/fibs/annotations, JSON export/import) into the codebase and own it, backed by the documented v5 primitives API; persist drawings as JSON via the Python backend. (2) User-defined indicators — do NOT build a JS eval sandbox as the primary path; since the backend is Python, let users write indicators in Python (pandas/numpy), computed server-side in a restricted subprocess and streamed to the frontend as plain series rendered in LWC v5 panes (indicator = computed series + pane placement + style). Optionally add a secondary in-browser JS indicator mode executed in a Web Worker (no DOM/network, postMessage in/out) — never bare new Function() on the main thread. (3) Strike/expiration overlays — built-in createPriceLine() for strikes plus a small custom pane primitive for vertical expiry lines/labels. (4) Payoff diagrams — separate component using Apache ECharts 6.1.0 (numeric x-axis, area fill above/below breakeven), not LWC. (5) Ship the TradingView attribution link (attributionLogo) to satisfy the NOTICE requirement. Name KLineCharts 10.0.1 in the requirements doc as the designated fallback if the drawing-layer fork proves too costly — it natively covers drawings + runtime custom indicators — accepting weaker multi-ticker overlay. Explicitly reject TradingView Advanced Charts (license incompatible with a personal, privately-distributed desktop exe), Highcharts Stock (~$833/dev), and Chart.js (financial plugin abandoned at 0.2.1).

## Options analytics (POP, margin, payoff)

Researched the math and integration facts for a multi-leg options trade panel. POP on retail platforms is not one formula: tastytrade integrates a terminal-price distribution against the expiration P/L (POP = P(profit ≥ $0.01)) and uses Monte Carlo for P50, thinkorswim exposes lognormal-based Probability ITM/OTM columns (N(d2)-style, distinct from delta which is N(d1)), and delta remains only a rough proxy. On libraries, the py_vollib ecosystem was renamed in mid-2026 (canonical package is now `vollib` 1.0.11; `py-vollib` 1.0.12 is a deprecation shim) while py-vollib-vectorized 0.1.1 (numba, Feb 2021, unmaintained) is still the fastest common full-chain IV/greeks path; QuantLib-Python is at 1.43 (BSD-3, abi3 wheels). For buying power, tastytrade's order dry-run returns the broker-computed BP effect (authoritative), Alpaca has no dry-run and no naked options at all, so RegT formulas must be computed locally for display; SPAN for futures options is proprietary and should come from the broker dry-run, not a local reimplementation.

**Recommendation:** Build the trade panel around a single normalized leg dataclass that feeds three consumers: (1) a POP engine that constructs the piecewise-linear expiration payoff, solves breakevens analytically, and integrates a lognormal terminal density for POP (label the method in the UI), with an optional Monte Carlo path simulator for P50 and calendar/diagonal strategies; (2) a greeks/IV service using numpy hand-rolled Black-Scholes + LetsBeRational via `vollib` (pin py-vollib-vectorized 0.1.1 only if full-chain numba speed proves necessary, and pin numba/numpy versions since it is unmaintained); (3) a BP-effect service that computes RegT formulas locally for instant display, then reconciles with tastytrade's POST /accounts/{n}/orders/dry-run (authoritative, also returns fees) before order submission -- for Alpaca the local calculation IS the display value since no dry-run exists and naked strategies must be gated off entirely. Treat SPAN margin for futures options as broker-supplied (tastytrade dry-run) with the 16-scenario scan-range grid only as a clearly-labeled estimate. Model SPX/SPXW/XSP as European/cash-settled (exact expiration payoffs, Black-76 pricing, AM vs PM settlement flag per series) and gate index options to tastytrade until Alpaca ships them live.

Key facts:
- POP methods in the wild: delta approximation P(ITM) ~= |delta| = N(d1) always overstates the risk-neutral ITM probability, which is N(d2) for calls / N(-d2) for puts (d1 - d2 = sigma*sqrt(T)); thinkorswim's Probability ITM/OTM columns are lognormal/moneyness-based (N(d2)-style) and Probability of Touching ~= 2x the ITM probability.
- tastytrade POP methodology (official support doc): POP = probability of making at least $0.01, computed by laying a distribution curve over the position's expiration P/L graph and integrating the profitable region; for mixed expirations it uses the distribution from the longest DTE; P50 (probability of reaching 50% of max profit before expiration) is computed via Monte Carlo simulation. The common credit-spread heuristic POP ~= 100% - (credit/width) matches this at entry.
- Recommended POP engine for the panel: build the strategy's piecewise-linear expiration payoff, find breakevens, then integrate a lognormal terminal density (using per-strike IV or ATM IV of the expiry) over the profitable region -- this reproduces both N(d2) single-leg results and tastytrade-style strategy POP; Monte Carlo (GBM paths) is only needed for path-dependent metrics like P50 and for multi-expiration strategies (calendars/diagonals).
- Python libraries (verified on PyPI 2026-08-01): canonical package is now `vollib` 1.0.11 (MIT, Peter Jaeckel LetsBeRational IV -- converges in ~2 iterations to machine precision, analytical+numerical greeks, Python >=3.9); `py-vollib` 1.0.12 (2026-06-01) is a deprecated compatibility shim that just depends on vollib.
- py-vollib-vectorized 0.1.1 (MIT, last release 2021-02-28, deps: py_vollib, numba, numpy, pandas, scipy) vectorizes the whole py_vollib API with numba and broadcasting -- documented as the fastest common library for pricing/IV across thousands of contracts (full chains); a newer alternative `fast-vollib` (arXiv 2604.27210, 2026) offers PyTorch/JAX/CUDA backends. Hand-rolled numpy Black-Scholes greeks are trivial and fully vectorizable; the hard part is robust IV inversion, which is exactly what LetsBeRational solves.
- QuantLib-Python 1.43 (released 2026-07-14, BSD-3-Clause) ships abi3 wheels for CPython 3.9+ (covers the user's Python 3.12) -- heavyweight (large binary for a packaged exe) and overkill for BS greeks, but the right tool if American-exercise/early-assignment-aware pricing is ever needed.
- RegT/strategy BP formulas (per contract x100 x qty, from CBOE margin manual / broker docs): naked put = max(20%*underlying - OTM_amount + premium, 10%*strike + premium, broker minimum $50-250); naked call same with 10%*underlying; cash-secured put = strike*100 - premium; credit vertical = width - credit (= max loss); debit vertical = debit paid; iron condor = greater of the call-spread and put-spread requirements (only one side is margined, net credit may be applied); covered call = no requirement on the short call, stock margined normally (50% RegT initial), buy-write BP = stock cost - premium.
- tastytrade API: POST /accounts/{account_number}/orders/dry-run returns broker-computed buying-power-effect with fields change-in-margin-requirement, change-in-buying-power, current-buying-power, new-buying-power, isolated-order-margin-requirement, is-spread, impact, effect, plus fee-calculation (clearing_fees, total_fees); GET /margin/accounts/{account_number}/requirements returns account margin grouped per underlying (margin-requirement, maintenance-requirement, reg-t-margin-requirement, option-buying-power, groups[]). The unofficial Python SDK tastyware/tastytrade is at v13.0.0 and exposes account.place_order(session, order, dry_run=True).
- Alpaca options (docs.alpaca.markets, 2026): dedicated options_buying_power field on the account; approval levels 0=disabled, 1=covered call/CSP, 2=+long calls/puts, 3=spreads/straddles; NO naked/uncovered options at any level; no dry-run/margin-preview endpoint exists, so the panel must compute BP effect locally (long options = premium in full, CSP = strike*100 - premium, defined-risk spreads = max loss). Effective level = min(options_approved_level, max_options_trading_level config).
- Alpaca index options: SPX, SPXW, VIX, VIXW, DJX, XSP are available in PAPER trading only (blog announcement); live trading is 'coming soon' -- live today is US equity/ETF American-style options only. tastytrade supports SPX/XSP and futures options live.
- SPX/XSP specifics the panel must model: European exercise (no early assignment -> expiration payoff diagrams are exact; price with Black-76 on the forward), cash-settled, Section 1256 60/40 tax treatment; SPX classic monthlies are AM-settled (stop trading Thursday, settle off Friday open -- overnight gap risk) while SPXW weeklies/dailies are PM-settled; XSP = 1/10 SPX size with the same properties. Multiplier 100 for both.
- Futures options margin: CME SPAN (now SPAN 2) is a proprietary 16-scenario portfolio simulation (price moves at fractions/multiples of the scan range crossed with vol up/down, worst-case loss = scanning risk); exact parameters are not public. Practical approximations: (a) authoritative -- use the tastytrade dry-run which returns broker-computed BP for futures options; (b) coarse local estimate -- scan-range grid: revalue the strategy at price shocks of +/-1/3, 2/3, 3/3 of the risk interval with vol shifted up/down and take the worst loss; (c) crudest -- risk_interval x contract_size x volatility factor.
- Payoff/chart data model: per-leg record {occ_symbol, underlying, right(C/P/stock), strike, expiration, signed_qty, entry_price, multiplier, current_mark, iv, delta/gamma/theta/vega, per_leg_pl}. Expiration P/L is piecewise-linear with kinks exactly at the sorted distinct strikes: evaluate P/L at each kink plus one point beyond each end; breakevens = linear interpolation where P/L crosses 0 between kinks; max gain/loss = extrema over kink values unless the terminal slope is nonzero (then unbounded, e.g. naked call upside); 'T+0'/intermediate curves = re-price every leg with BS over a spot grid at the chosen date/vol. Chart overlays derive from the same records: horizontal strike lines per leg (styled by long/short and C/P), expiration vertical lines on the time axis, breakeven and spot markers, expected-move cone S*IV*sqrt(DTE/365) bands. Keeping per-leg payoff arrays separate gives per-leg contribution display for free (total = sum).

Risks / constraints:
- py-vollib-vectorized has had no release since Feb 2021 and depends on the now-deprecated py_vollib name plus numba -- numba/numpy version compatibility on Python 3.12 must be tested and pinned before committing to it; fall back to plain vollib + numpy vectorization if it breaks.
- The py_vollib -> vollib rename (mid-2026) means tutorials and older code import the deprecated shim; standardize on `vollib` imports now to avoid a future breakage.
- QuantLib adds a very large binary dependency to a packaged Windows executable -- only include it if American-exercise pricing is a firm requirement.
- POP is model-dependent: delta, N(d2), and distribution-integration give visibly different numbers, and tastytrade's own displayed POP uses house distribution assumptions -- the panel will never exactly match broker-displayed values, so show the calculation method and never present the local number as the broker's.
- RegT formulas are exchange MINIMUMS; brokers apply house margin (tastytrade concentration/house rules, per-contract minimums varying $50-250), so local BP numbers are estimates -- the tastytrade dry-run must be the pre-submit source of truth, and its absence on Alpaca means Alpaca BP display carries estimate risk.
- Alpaca prohibits naked/uncovered options at every level and index options are paper-only as of 2026-08 -- strategy availability must be gated per broker or orders will be rejected.
- SPAN/SPAN 2 parameters are proprietary; any local approximation can drift far from actual futures-option margin, especially after volatility spikes when CME resets scan ranges.
- SPX AM-settled monthlies (trading halts Thursday, settle off Friday open) will produce wrong expiration P/L and POP if the panel treats all SPX series as PM-settled -- the series (SPX vs SPXW) must carry a settlement-type field.
- Multi-expiration strategies (calendars, diagonals) have no pure expiration payoff -- max gain/loss and POP require model-based revaluation of the far leg at the near expiry, which is estimate-quality, not exact.
- Webull and Fidelity were out of scope for this subtask; nothing here confirms they expose margin-preview or options-chain APIs comparable to tastytrade/Alpaca.

## Omnibox search stack

Verified a two-tier omnibox stack: keystroke-level lexical matching (in-memory prefix index + RapidFuzz 3.14.5 over ~11k ticker symbol+name strings, plus SQLite FTS5 trigram for substring/news/page matching) comfortably fits under 30ms, while a debounced semantic tier (fastembed 0.8.0 ONNX with all-MiniLM-L6-v2, or Model2Vec potion static embeddings for microsecond encoding) reranks the top candidates and fuses via Reciprocal Rank Fusion (k=60). The ticker universe comes free from Alpaca GET /v2/assets (symbol, name, exchange, tradable, asset_class) using the paper keys the user already has. All recommended components are MIT/Apache licensed and PyTorch-free, so they package cleanly into a Windows executable.

**Recommendation:** Build the omnibox as a two-tier pipeline in the Python backend. Tier 1 fires on every keystroke: (a) exact/prefix hit on an in-memory dict/trie of ~11k Alpaca symbols, (b) rapidfuzz process.extract (WRatio, score_cutoff~70, limit~20) over concatenated 'SYMBOL name' strings, (c) SQLite FTS5 with trigram tokenizer over app pages, AI-action descriptions, and cached news headlines (route queries under 3 chars to prefix-only). Tier 2 fires after a 150-200ms debounce: embed the query with fastembed (all-MiniLM-L6-v2 ONNX, bundled with the installer to avoid first-run download) — or swap to Model2Vec potion-retrieval if profiling on low-end CPUs shows MiniLM exceeding budget — then brute-force cosine against precomputed embeddings stored in sqlite-vec (or a plain numpy float32 matrix, which removes the pre-v1 dependency risk entirely), and merge all result lists with RRF (k=60). Run a deterministic intent grammar before ranking: token-match against the ticker dictionary plus an intent keyword lexicon so 'SPY news' routes to a ticker-scoped news search pinned above fused results. Source the ticker universe from Alpaca GET /v2/assets?status=active&asset_class=us_equity (paper keys suffice), cache it in SQLite, refresh daily. Skip ChromaDB and LanceDB — both add packaging weight for no benefit at this scale.

Key facts:
- RapidFuzz 3.14.5 (released 2026-04-07, MIT license, Python 3.10-3.14) is C++/SIMD-backed; at ~10k records fuzzy matching is single-digit-milliseconds territory and the docs state batch processors (process.extract/process.cdist) are much faster than calling scorers directly; O(N^2)/large-N use (100k+ rows) degrades badly, so keep the fuzzy scan to the ~10k ticker universe only.
- SQLite FTS5 ships a built-in 'trigram' tokenizer enabling arbitrary substring (LIKE/GLOB-accelerated) matching; measured ~1.75s over 18.2M rows implies well under 5ms at omnibox scale (tens of thousands of rows); caveats: query tokens under 3 unicode chars match nothing (must route 1-2 char queries to prefix matching), and the trigram index roughly triples table storage size (irrelevant at this scale).
- all-MiniLM-L6-v2: ~22M params, 384-dim, ~90MB; CPU throughput ranges ~50 sentences/sec single-thread (~20ms/sentence) to ~14k sentences/sec batched multi-thread — a single query embedding is roughly 10-30ms on a typical desktop CPU, so it must sit behind a debounce, not on every keystroke.
- fastembed 0.8.0 (released 2026-03-23, Apache-2.0, Python 3.10-3.14) runs embeddings on ONNX Runtime with quantized models — explicitly no PyTorch dependency and ~5x throughput over raw HuggingFace Transformers — making it the right embedding runtime for a PyInstaller-style Windows executable.
- Model2Vec/potion static embeddings (MinishLab, MIT): potion-base-8M is ~8MB, ~90% of MiniLM quality, ~500x faster (tens of thousands of sentences/sec, microseconds per query); potion-retrieval-32M is the best static retrieval model — the strongest option if semantic scoring must run on every keystroke rather than debounced.
- sqlite-vec (Alex Garcia): pure-C zero-dependency SQLite extension, pip-installable, dual MIT/Apache-2.0, runs on Windows; still pre-v1 ('expect breaking changes'); brute-force KNN is its reliable mode — fine for <100k vectors, which covers this use case; ChromaDB is in-memory-architecture and dependency-heavy, LanceDB is disk-based IVF-PQ for larger-than-RAM data — both are overkill for an omnibox index of tens of thousands of entities.
- Reciprocal Rank Fusion is the industry-default hybrid fusion (Elasticsearch, OpenSearch, Azure AI Search, MongoDB Atlas, Weaviate): score = sum over lists of 1/(k + rank), k=60 standard and insensitive across k in [20,100]; it fuses BM25/fuzzy and vector lists by rank position alone, eliminating score-normalization problems between rapidfuzz scores, FTS5 bm25(), and cosine similarity.
- Alpaca GET /v2/assets is the master list of all tradable assets and returns symbol, name, exchange, tradable, status, asset_class (us_equity, us_option, crypto, and more) with filters status=active&asset_class=us_equity; it works with paper-trading keys (which the user has) at no cost; Trading API rate limit is 200 requests/min (429 on excess), irrelevant for a once-daily refresh of the ~11k-symbol universe.
- Recommended concrete stack — Tier 1 (every keystroke, <30ms): in-memory exact/prefix dict on symbols (<1ms) + rapidfuzz process.extract with score_cutoff over ~11k 'SYMBOL Company Name' strings (~5-10ms) + FTS5 trigram over app pages/AI actions/cached news headlines (~1-5ms). Tier 2 (debounced 150-200ms, <60ms): embed query with fastembed MiniLM (or potion-8M for zero-latency), brute-force cosine over precomputed entity embeddings in sqlite-vec or a numpy matrix, fuse all lists with RRF k=60. Intent grammar runs before ranking: tokenize, match tokens against the ticker dictionary and an intent lexicon (news/chart/buy/options/ai), so 'SPY news' deterministically pins a ticker-scoped news action at rank 1 with hybrid results below.
- End-to-end latency budget: keystroke to lexical dropdown paint <30ms; debounce 150ms; semantic rerank + RRF + re-paint <60ms; worst-case perceived latency ~250ms with lexical results visible from the first frame — within the 100ms-per-computation-stage rule for as-you-type UIs.

Risks / constraints:
- sqlite-vec is pre-v1 with explicit 'expect breaking changes' warning; its ANN indexing is immature — rely only on brute-force KNN, or sidestep it with a numpy dot-product over an in-memory float32 matrix (~15MB for 100k x 384-dim vectors).
- FTS5 trigram tokenizer returns nothing for query tokens shorter than 3 unicode characters — 1-2 character queries (very common for tickers) must be handled by the prefix/fuzzy tier, never by FTS5.
- MiniLM query-embedding latency is CPU-dependent: ~10-20ms on a modern desktop but can reach 50ms+ single-threaded on low-end hardware — keep it debounced and profile on target machines; Model2Vec fallback costs ~10% retrieval quality.
- fastembed downloads models from HuggingFace on first use (~90MB for MiniLM) — bundle the ONNX model files inside the Windows installer or first launch breaks offline/behind-proxy.
- Semantic embeddings are weak on raw ticker strings ('NVDA' has little semantic content) — use the semantic tier for company names, news, app pages, and AI actions; keep symbols on the lexical tier, and blend via RRF rather than letting cosine scores dominate.
- Alpaca /v2/assets requires authenticated keys (no anonymous access) and shares the 200 req/min Trading API limit — cache the universe locally and refresh at most daily; also note Alpaca's list covers Alpaca-tradable US equities/options/crypto, so symbols only on Webull/Fidelity (e.g., some OTC or international names) would need a supplemental source later.
- RapidFuzz full-scan cost is linear in corpus size — fine at 10-15k tickers, but do not extend the fuzzy scan to news headlines or large corpora (100k+ rows showed multi-minute batch times in benchmarks); FTS5 covers those.
- ChromaDB pulls a heavy dependency tree and holds indexes in memory; LanceDB's Rust/Arrow stack adds packaging complexity for a Windows exe — both are unnecessary below ~1M vectors and would bloat the PyInstaller bundle.
- Licensing is clean across the stack (RapidFuzz MIT; fastembed Apache-2.0; sqlite-vec MIT/Apache-2.0 dual; Model2Vec MIT; SQLite public domain; all-MiniLM-L6-v2 Apache-2.0), but verify the specific embedding model card license if swapping models — some HF embedding models (e.g., certain bge/gte variants) have changed license terms between versions.

## Packaging, installer, auto-update

Researched Windows packaging/auto-update for an Electron shell with a Python sidecar as of Aug 2026. The proven stack is: PyInstaller 6.21 onedir (never onefile, for AV reasons) or an Astral python-build-standalone runtime for the sidecar; electron-builder 26.15.x NSIS per-user installer (the only Windows target electron-updater supports — Squirrel.Windows is deprecated); electron-updater with the generic HTTPS provider and blockmap differential updates; and Azure Artifact Signing (formerly Trusted Signing, $9.99/mo, open to US/Canada individuals) to solve both SmartScreen and update-verification problems. OpenWebUI should not be frozen with PyInstaller — it is pip-installable (`open-webui serve`, Python 3.11) and should run from an app-managed CPython env in LocalAppData; its v0.6.6+ license adds a branding clause that a ≤50-user desktop deployment is exempt from, but the official open-webui/desktop app is AGPL-3.0 (do not copy its code).

**Recommendation:** Ship as: Electron shell + electron-builder (26.x) NSIS one-click per-user installer (perMachine:false, no admin) + electron-updater with the generic HTTPS provider (host latest.yml + Setup.exe + .blockmap on any static host; blockmap gives delta updates for free, including sidecar changes). Sign from day one with Azure Artifact Signing Basic ($9.99/mo — Kade, as a US individual, is eligible; validation via government ID takes days, so start early): it removes the SmartScreen 'Unknown publisher' wall, enables electron-updater's signature verification (otherwise updates are unauthenticated), and avoids the $220-500/yr token-based cert path whose EV advantage no longer exists. Bundle the trading backend as a PyInstaller 6.x onedir build in extraResources (never onefile — AV false positives), spawned on a dynamic localhost port with a shared auth token. Do NOT freeze OpenWebUI: run it from an app-managed python-build-standalone 3.11 runtime + uv-created env in %LOCALAPPDATA%, started via `open-webui serve --port <dynamic>` with an HTTP health check and pre-bundled embedding model (offline env vars set); update that env out-of-band from the Electron installer so ML dependencies don't balloon every app update. Fork/refactor OpenWebUI from the current line relying on the ≤50-user rebranding exception (or from v0.6.5 BSD-3 if future distribution beyond 50 users is conceivable), and take nothing from the AGPL-3.0 open-webui/desktop repo. Skip MSIX and Squirrel.Windows entirely; reconsider MSIX only if the app ever goes to the Microsoft Store.

Key facts:
- PyInstaller current release is 6.21.0 (2026-06-13), actively maintained. Its --onefile mode self-extracts to a temp dir at runtime, which trips antivirus heuristics; the shared bootloader is what AV vendors fingerprint. Official/community guidance (updated April 2026): use onedir (the default), wrap in an installer, and report false positives to AV vendors. For an Electron sidecar, onedir output hidden inside the app's resources folder is the natural fit — onefile buys nothing.
- python-build-standalone is now stewarded by Astral (took over from Gregory Szorc 2024-12-17); its builds are truly standalone (download, unzip, run), power uv/pipx/Hatch/mise/Bazel, and have 70M+ downloads. Bundling one of these runtimes plus pip-installed packages avoids the PyInstaller bootloader AV problem entirely and makes the sidecar a plain file tree that is easy to delta-update. The python.org 'Windows embeddable package' also exists but ships without pip and needs ._pth surgery.
- Nuitka is Apache-2.0 with a commercial tier (~EUR 250/yr) that adds obfuscation and IP-protection features; it still suffers unsigned-binary AV false positives (GitHub issues #1470, #2163, #2757) and has long compile times. It is an IP-protection/performance play, not an AV fix — overkill for a sidecar.
- electron-builder current version is 26.15.x (npm, mid-2026). Its NSIS target is the ONLY Windows target electron-updater supports for auto-update ('Squirrel.Windows is not supported... Simplified auto-update is supported on Windows if you use the default NSIS target'). Squirrel.Windows itself last released Sep 2020 and is deprecated by both electron-builder and electron-forge maintainers (forge issues #3069, #3598).
- electron-builder NSIS per-user install without admin: perMachine:false (the default) with the default oneClick installer installs to %LOCALAPPDATA% with no elevation; oneClick:false + perMachine:false shows a chooser page. Auto-update of per-MACHINE installs has known elevation bugs (issues #5644, #6312, #5796) — per-user is the reliable auto-update path.
- electron-updater generic HTTP provider needs only static HTTPS hosting of three files per release: latest.yml, the NSIS Setup.exe, and Setup.exe.blockmap. Differential updates are on by default: the updater diffs old vs new blockmap and fetches only changed blocks via HTTP range requests (disableDifferentialDownload forces full). Because the NSIS update reinstalls the whole app directory, a changed Python sidecar in extraResources ships automatically — unchanged sidecar blocks are not re-downloaded, so 'delta vs full' is handled at block level. Known failure: differential update degrades to full when compressed assets change wholesale (issue #3490).
- electron-updater unsigned behavior on Windows: verifyUpdateCodeSignature (default true) embeds the publisher name from the build-time signing cert into app-update.yml; at update time the downloaded installer's Authenticode subject must match or install is refused ('New version is not signed by the application owner'). If the build is UNSIGNED, no publisher name is embedded and verification is silently skipped — updates still install, but with zero cryptographic authentication of the update binary (HTTPS is the only protection; there is a history of verification-bypass bugs, e.g. issue #4701/Doyensec). Corollary: switching certificates later breaks auto-update for existing installs, so certificate continuity must be planned.
- Azure Trusted Signing was renamed Azure Artifact Signing and is GA (docs updated 2026-05-21). Basic plan: $9.99/month for 5,000 signatures ($0.005/extra). Individual developers ARE eligible but must be located in the United States or Canada; organizations: US, CA, EU, UK, AU, NZ, JP, KR, SG, CH, NO, IL. Individual identity validation is done in the Azure portal via AU10TIX government-ID + Microsoft Verified ID (mobile phone flow); the Azure billing account must be Account Type 'Individual' and exactly match the ID; processing takes 1-20 business days. Certificates are short-lived (renewed daily) and timestamped, and signatures carry base SmartScreen reputation.
- Traditional certs 2026: OV code signing ~$65-230/yr (Certum/SSL.com cheap end, Sectigo ~$220), EV ~$249-500/yr; since June 2023 CA/B Forum rules require private keys on FIPS 140-2 L2 hardware (shipped token, your own YubiKey/HSM, or cloud KMS). Microsoft REMOVED the EV instant-reputation advantage in 2024 — as of July 2026 its SmartScreen docs state OV and EV build reputation identically, which kills the main argument for EV.
- Unsigned SmartScreen reality: 'Unknown publisher' interstitial on first install; reputation for unsigned files is per-file-hash, so it resets to zero with EVERY release; building it takes weeks and hundreds of clean installs. Signed files accrue reputation on the certificate, which compounds across releases. As of July 2026 Microsoft's Security Intelligence portal accepts direct developer file submissions to clear false verdicts. Real-world example: Open WebUI's own desktop installer triggers SmartScreen (open-webui/desktop issue #117). Note: electron-updater's own silently-executed downloads do not get browser Mark-of-the-Web, so the SmartScreen pain concentrates on FIRST install, not updates.
- MSIX: requires a CA-trusted code signature (unsigned/self-signed packages cannot install without users manually trusting the cert), installs per-user without admin by default, and gets free auto-update via a hosted .appinstaller file — but electron-updater does not support it, and MSIX containerization complicates a Python sidecar. Inno Setup (6.5.x current, Inno Setup 7 arriving ~July 2026) supports per-user via PrivilegesRequired=lowest but has no electron-updater integration. Both are viable only with a custom updater.
- OpenWebUI local bundling: installable via `pip install open-webui`, started with `open-webui serve --port NNNN` (default 8080; PORT env also works); requires Python 3.11 (docs' uvx examples pin --python 3.11; v0.35 added a tf-keras dependency); DATA_DIR env controls where webui.db (SQLite) and uploads live. Freezing it with PyInstaller is impractical (huge ML dependency tree); the workable pattern is: ship a python-build-standalone 3.11 runtime, create/populate the env in %LOCALAPPDATA% (uv makes this fast), spawn `open-webui serve` on a dynamically chosen localhost port, and health-check the HTTP endpoint before showing UI. Known startup costs: cold starts of 10+ seconds, first-run DB migrations, and a first-run embedding-model download that fires even in offline mode unless HF offline env vars are set or the model is pre-bundled (issue #21405); model-list page loads take 10-15s without model caching.
- OpenWebUI licensing for a 'refactored/integrated' build: v0.6.6+ (April 2025) uses the 'Open WebUI License' — BSD-3 plus a branding-protection clause (may not alter/remove 'Open WebUI' name/logo/identifiers). Critical exception: deployments with 50 or fewer users in a rolling 30-day period MAY fully rebrand — a personal desktop trading app qualifies. Code through v0.6.5 remains plain BSD-3 and freely forkable; contributions after v0.6.5 require a CLA; enterprise license available for at-scale rebranding. Separately, the official open-webui/desktop Electron app (early alpha, bundles llama.cpp, Windows x64/ARM64) is AGPL-3.0 — copying code from it would drag the whole platform into AGPL.
- Electron + Python sidecar wiring (established pattern, e.g. Simon Willison's writeup and the electron-flask/python-electron examples): put the onedir sidecar under extraResources, resolve it via process.resourcesPath, spawn as child process, choose a free port (bind port 0 or scan) and pass it plus a randomly generated auth token to both the sidecar and renderer, and kill the child on app quit (onefile would leave orphanable extraction processes — another reason to avoid it).

Risks / constraints:
- Unsigned builds make electron-updater updates cryptographically unverified (verification is skipped when no publisher name is embedded) — HTTPS on the update host is the only protection, and the code path has had bypass CVEs (electron-builder #4701). Signing is the mitigation.
- Certificate continuity: once signed, every future update must be signed by a cert with the same publisher subject, or installed apps refuse the update ('not signed by the application owner'). Switching from unsigned to signed, or between certs, strands existing installs on manual reinstall.
- Azure Artifact Signing individual eligibility is US/Canada only, requires the Azure billing account type to be 'Individual' with details exactly matching a government ID, and identity validation can take 1-20 business days; the AU10TIX flow needs a supported mobile device. Also the service was renamed from 'Trusted Signing' — older docs/tutorials use the old name and CLI extension names.
- Even signed apps start with 'Publisher unknown' until the certificate accrues SmartScreen reputation (weeks / hundreds of installs); EV no longer shortcuts this (removed 2024).
- PyInstaller onedir reduces but does not eliminate AV false positives; occasional Defender flags still need submission to Microsoft's Security Intelligence portal (accepts developer submissions as of July 2026).
- OpenWebUI v0.6.6+ branding clause: the ≤50-user (rolling 30-day) exception covers a personal app, but any future distribution of a rebranded build beyond 50 aggregate users would violate the license without an enterprise agreement; the project is no longer OSI open source and requires a CLA upstream. Fork point v0.6.5 (BSD-3) is the escape hatch but forfeits later features.
- open-webui/desktop is AGPL-3.0 — reusing its bundling code would impose AGPL on the whole platform.
- electron-updater differential updates silently fall back to (or fail toward) full downloads when large compressed assets change (#3490); bundling OpenWebUI's ML dependency tree in the installer would make every update effectively full-size — keep it out of the installer.
- Per-machine NSIS installs have long-standing auto-update elevation bugs in electron-builder (#5644, #6312); stay per-user.
- OpenWebUI cold start is 10+ seconds with first-run migrations and an embedding-model download that fires even offline unless pre-bundled/env-disabled — the shell needs a splash/health-check state, and first-run needs network or a bundled model.
- MSIX cannot be used unsigned at all, and Squirrel.Windows is unmaintained (last release Sep 2020) — avoid templates/boilerplates built on either.
- Inno Setup is mid-transition to v7 (banner from July 2026); if a custom non-electron-updater installer were chosen, target the v7 line.

## Auth & secret storage

Researched auth and secret storage for a local Windows desktop trading app (Electron/web frontend + local FastAPI backend). Verified current library versions and capabilities: argon2-cffi 25.1.0 for both password hashing and KEK derivation, keyring 25.7.0/Windows Credential Manager (2560-byte blob limit), DPAPI via pywin32, and SQLCipher on Windows via the community sqlcipher3-wheels package (official sqlcipher3-binary ships manylinux wheels only; pysqlcipher3 is explicitly unmaintained). The standard, correct pattern for recoverable broker keys is envelope encryption: a random per-user DEK encrypts key material with AES-256-GCM; the DEK is wrapped by a KEK derived from the login password via argon2id (hash_secret_raw), with an optional second DPAPI wrap for convenience unlock; keys are never hashed. For port protection, verified that localhost cookies are shared across ports (RFC 6265 §5.1.3) and DNS rebinding against localhost HTTP servers is an active 2025-2026 attack class (e.g. CVE-2025-66414 in the MCP TypeScript SDK), so bearer tokens + Host-header validation + 127.0.0.1 binding + random port is the right design, not session cookies.

**Recommendation:** Adopt this concrete design. (1) Auth: SQLite users table storing username + argon2id hash from argon2-cffi 25.1.0 PasswordHasher defaults (RFC 9106 low-memory: 64 MiB, t=3, p=4) + a separate random 16-byte kdf_salt + a KEK-wrapped DEK blob per user. On login, verify the hash, then derive a 32-byte KEK with argon2.low_level.hash_secret_raw(Type.ID, same cost params, kdf_salt) and unwrap the user's random 32-byte DEK (AES-256-GCM). (2) Secrets at rest: encrypt each broker credential (Alpaca/TastyTrade/Webull/Fidelity keys and tokens) individually with AESGCM(DEK), fresh 96-bit nonce, AAD = user_id||field_name; never store or log plaintext; the phrase in requirements should be 'encrypted at rest under a password-derived key', not 'hashed'. Offer an opt-in 'skip password on this machine' that additionally wraps the DEK with DPAPI (pywin32 CryptProtectData) and stores that blob in %LOCALAPPDATA% (outside any synced folder); default it off for a trading app. Do not make Windows Credential Manager/keyring the primary vault (2560-byte blob cap, same-user-readable); optionally keep only the DPAPI convenience blob there. (3) Port protection: uvicorn bound to 127.0.0.1 on an OS-assigned random port; Electron main spawns the backend, passes a 256-bit bootstrap secret via stdin/env, receives the port back on stdout; every request requires Authorization: Bearer <session token> (opaque, random, in-memory table, no cookies, no JWT); add TrustedHostMiddleware(allowed_hosts=['127.0.0.1','localhost']) against DNS rebinding; send no CORS headers; renderer gets the token only through a preload contextBridge. (4) Auto-lock: on 10-15 min system idle (powerMonitor) or Windows lock-screen event, revoke all sessions and best-effort-wipe DEK/KEK (bytearray overwrite); unlock = password re-entry. (5) Database: use plain SQLite with app-layer field encryption as the baseline — it is fully deterministic, pure-`cryptography`, and protects exactly what matters if the DB file is synced or stolen (everything sensitive is AES-GCM ciphertext under an argon2id-derived key). Treat full-file SQLCipher via sqlcipher3-wheels as an optional hardening layer for hiding trade history/metadata, and if adopted, pin the version and vendor the wheel because Windows coverage depends on a community fork; avoid pysqlcipher3 entirely.

Key facts:
- argon2-cffi latest stable is 25.1.0; its PasswordHasher defaults follow RFC 9106's SECOND RECOMMENDED (low-memory) profile — Argon2id, 64 MiB memory, parallelism 4 — and the docs recommend Argon2id (Type.ID) as the default variant (https://argon2-cffi.readthedocs.io/en/stable/parameters.html).
- argon2-cffi also serves as the KDF: argon2.low_level.hash_secret_raw() derives a raw 32-byte key from password+salt, which is the standard way to build a KEK for Fernet or AES-GCM; use a KDF salt separate from the login-hash salt so the verifier and the encryption key are independent.
- Broker API keys must be encrypted, not hashed — hashing is one-way and the app must present the real key to Alpaca/TastyTrade. The standard pattern is envelope encryption: random 32-byte DEK encrypts each secret with AES-256-GCM (cryptography.hazmat AESGCM, fresh 96-bit nonce per value, AAD binding user/field); DEK is stored wrapped by the password-derived KEK; login unwraps DEK into memory.
- Windows DPAPI (pywin32 win32crypt.CryptProtectData / CryptUnprotectData) encrypts per-user, per-machine: only the same Windows user on the same machine can decrypt, keys live under %APPDATA%\Microsoft\Protect\{SID} (https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata). It is the right tool for an optional convenience-unlock wrap of the DEK (the Chrome os_crypt pattern), but any process running as that user can also call CryptUnprotectData — it does not defend against same-user malware and a DPAPI blob is useless if the DB file is synced/stolen off-machine (which is the desired property).
- python keyring latest is 25.7.0 (released 2025-11-16, Python >=3.9); on Windows it backs onto the Credential Locker/Credential Manager. Hard limit verified: CRED_MAX_CREDENTIAL_BLOB_SIZE = 5*512 = 2560 bytes per credential (https://learn.microsoft.com/en-us/windows/win32/api/wincred/ns-wincred-credentialw), and stored secrets are readable by ANY process running as the logged-in user — there is no per-app ACL. Suitable for small bootstrap secrets, not as the primary vault design.
- SQLCipher via Python on Windows in 2026: pysqlcipher3 README explicitly says 'no longer being actively maintained... use at your own risk' (https://github.com/rigglemania/pysqlcipher3). coleifer's sqlcipher3 is the live binding, but the official binary package sqlcipher3-binary (0.6.0, 2025-12-31) ships manylinux x86-64 wheels ONLY — no Windows wheels. The community fork sqlcipher3-wheels 0.5.7 (released 2026-01-07) ships Windows x86/x64/ARM64 wheels bundling SQLCipher 4, Python 3.8-3.14 incl. free-threaded, zlib/libpng license (https://pypi.org/project/sqlcipher3-wheels/).
- Cookies are NOT scoped by port (RFC 6265 §5.1.3: 'the port is not included in the scope of a cookie'), so a session cookie set by localhost:<appport> is sent to every other localhost server and vice versa — a decisive argument against cookie sessions for a localhost API; use an Authorization: Bearer header instead, which also makes browser-driven CSRF structurally impossible (no ambient credential).
- DNS rebinding against localhost HTTP servers is a current, actively exploited class: CVE-2025-66414 (CVSS 7.6, Dec 2025) hit the MCP TypeScript SDK exactly this way — HTTP-only local server, no Host validation (https://github.blog/security/application-security/localhost-dangers-cors-and-dns-rebinding/). Mitigations: bind uvicorn to 127.0.0.1 only, validate the Host header (Starlette/FastAPI TrustedHostMiddleware, allowed_hosts=['127.0.0.1','localhost']), require the bearer token on every route including token issuance, and return no CORS headers (default-deny) so browser pages cannot read responses.
- Random-port + per-launch bootstrap token is an established Electron+Python pattern: the Electron main process generates a random token, hands it to the spawned Python server via stdin or environment (never argv — visible in Task Manager/process list) and to the renderer via contextBridge/IPC; the OS-assigned ephemeral port (bind port 0) is reported back the same channel (pattern documented e.g. in https://github.com/yoDon/electron-python).
- JWT vs opaque token on localhost: JWT buys nothing locally (no third party needs to verify claims, and revocation requires a denylist anyway). A 256-bit random opaque token checked against an in-memory session table in the FastAPI process is simpler, instantly revocable on logout/auto-lock, and leaves no signed artifact to leak. If JWT is used anyway, sign HS256 with a per-launch random secret and keep expiry short (~15 min) with refresh.
- Auto-lock design: Electron's powerMonitor.getSystemIdleTime() gives system-wide idle seconds; on N-minute idle or OS lock-screen event ('lock-screen' on Windows), the backend invalidates all session tokens and drops the DEK/KEK from memory, forcing password re-entry (which re-derives the KEK and re-unwraps the DEK). Python cannot guarantee zeroization of immutable bytes objects — use bytearray and overwrite as best-effort, and document it as such.
- Multiple user profiles map cleanly onto envelope encryption: one users row per profile (argon2id login hash + per-user KDF salt + per-user wrapped DEK); each user's broker keys are encrypted under their own DEK, so profiles cannot read each other's keys even with full DB file access, and an admin/password-reset flow cannot silently recover another user's keys (re-enrollment of broker keys after reset is mandatory and should be stated in requirements).

Risks / constraints:
- Any malware running as the same Windows user defeats every option here (DPAPI, Credential Manager, keyring, and in-memory DEKs are all same-user-readable) — the OS user account is the real security boundary and the requirements doc should say so explicitly rather than implying the app can resist a compromised machine.
- Password loss = broker-key loss by design: with keys encrypted under a password-derived KEK there is no recovery path except the DPAPI convenience wrap on the same machine; requirements must include a reset flow that deletes and re-enrolls broker keys rather than pretending to recover them.
- Windows SQLCipher wheels come from a community fork (sqlcipher3-wheels, zlib license); the official sqlcipher3-binary has no Windows wheels and pysqlcipher3 is abandoned with an explicit security disclaimer — a supply-chain and maintenance risk if SQLCipher is made load-bearing; also SQLCipher key management still reduces to the same password/DPAPI question, so it adds ops burden without removing the KDF design.
- Cookies must not be used for localhost sessions: RFC 6265 scopes cookies by host only, not port, so any other local server (or a rebinding page) shares the cookie jar with the app's port; the design must stay bearer-token-only, and the token must never be passed on the command line (process-list visible) or persisted to disk.
- DNS rebinding mitigations depend on discipline: Host-header validation has to cover every route including token/bootstrap endpoints (the MCP SDK CVE showed a single unvalidated mount reopens the hole), and browser-side protections (Chrome Local Network Access) cannot be relied on across browsers in 2026.
- argon2id at RFC 9106 low-memory costs 64 MiB RAM per derivation; simultaneous profile logins or an aggressive auto-lock/unlock loop can spike memory on a machine that is also running charts and backtests — acceptable for single-user desktop but worth stating the parameters in the requirements so they are tuned deliberately.
- Python cannot guarantee memory zeroization (immutable bytes may be copied by the runtime); auto-lock 'wipes' are best-effort, and a memory dump while unlocked exposes the DEK — do not claim stronger guarantees in the requirements.
- If the SQLite DB lives in a Google-Drive-synced folder (as this workspace's conventions make likely), sync happens by design — the DPAPI-wrapped DEK and any session artifacts must be written outside the synced tree, and the requirements should mandate a directory-placement rule, not rely on convention.

## News pipeline & knowledge base

Verified the full news-to-AI pipeline against current docs (2026-08-01). Alpaca's Benzinga-sourced News API gives REST history back to 2015 at https://data.alpaca.markets/v1beta1/news plus a websocket stream at wss://stream.data.alpaca.markets/v1beta1/news, with optional full-HTML content. OpenWebUI v0.11.0 exposes a complete Knowledge REST API (create collection, upload file, add/update/remove file, per-file re-embedding, reindex) with async processing that must be polled before adding files. For the desktop-local vector store LanceDB (0.36.0, Apache-2.0, in-process, native BM25 FTS + hybrid) beats Chroma and pgvector; trafilatura 2.2.0 (now Apache-2.0) is the extraction pick over newspaper4k. The right architecture is a two-tier split: a live MCP tool hitting Alpaca REST for breaking news, and KB semantic search for anything older than the ingestion lag.

**Recommendation:** Build a two-tier news pipeline with a clean freshness split. Tier 1 (live): a Python ingester subscribes to wss://stream.data.alpaca.markets/v1beta1/news (wildcard) and writes every article into a local LanceDB table (one chunk per article, headline prepended, metadata: symbols, source, created_at, updated_at, url; upsert keyed on Alpaca id, re-embed on updated_at change; call table.optimize() on a timer so FTS covers new rows). Expose an MCP tool (streamable HTTP, so both OpenWebUI >=0.6.31 and Claude Code can use it) named e.g. latest_news(symbols, lookback) that queries Alpaca REST v1beta1/news directly with include_content=true — this answers 'what just happened' with zero indexing lag and stays well inside the 200 req/min free-tier limit. Tier 2 (knowledge): a scheduled pusher (every 15-60 min) batches recent articles into per-day or per-week text files and syncs them into an OpenWebUI knowledge collection via POST /api/v1/files/ then poll /api/v1/files/{id}/process/status until completed, then POST /api/v1/knowledge/{id}/file/add (or /file/update to replace the current day's rolling file — it deletes old vectors and re-embeds). Keep a 60-90 day rolling window in the KB using /file/remove for expired files, and archive older raw JSON to disk. Prompt the AI (system prompt / tool descriptions) with the split: use the MCP tool for anything in the last few hours, KB search for older context. For full-article reads beyond Benzinga's content field, add an MCP tool wrapping trafilatura 2.2.0 (Apache-2.0) on the article's url field, with newspaper4k as optional fallback/discovery. Use LanceDB (not Chroma, not pgvector) as the platform's own vector store: it is in-process (no server to bundle in the Windows exe), disk-based, Apache-2.0, and gives hybrid BM25+vector retrieval — ideal for ticker-symbol keyword matching plus semantic search. Note OpenWebUI runs its OWN internal chunking/embedding store for Knowledge collections, so don't try to share the LanceDB store with it; treat OpenWebUI KB and the MCP-side LanceDB as two sinks fed by one ingester.

Key facts:
- Alpaca News REST: GET https://data.alpaca.markets/v1beta1/news (sandbox: data.sandbox.alpaca.markets). Params: symbols (comma list, stocks+crypto), start/end (RFC-3339), limit 1-50 (default 10), sort (default desc by updated), include_content (bool), exclude_contentless (bool), page_token. Response fields: id, headline, author, created_at, updated_at, summary, content, url, images (thumb/small/large), symbols[], source; next_page_token for pagination.
- Alpaca news content field: full article body as HTML, but ONLY when include_content=true; some articles are contentless (filter with exclude_contentless). All news is provided by Benzinga.
- Alpaca news historical depth: back to 2015, averaging 130+ articles/day (per docs.alpaca.markets/docs/historical-news-data).
- Alpaca real-time news websocket: wss://stream.data.alpaca.markets/v1beta1/news, auth via APCA-API-KEY-ID/APCA-API-SECRET-KEY at handshake, subscribe with {"action":"subscribe","news":["*"]} or per-symbol list. Message schema mirrors REST (T, id, headline, summary, content, url, symbols, source).
- Alpaca news rate limits: tied to the market-data subscription — 200 req/min on Free plan, 10,000 req/min on paid/unlimited (Alpaca blog); the API reference also cites 100 req/min baseline with X-RateLimit-* headers. Kade already has Alpaca keys, so the free tier covers a polling cadence of every few seconds.
- OpenWebUI current release: v0.11.0 (2026-07-27). Auth for all APIs: Authorization: Bearer <API key from Settings > Account> (or JWT).
- OpenWebUI file upload: POST /api/v1/files/ (multipart), query params process=true and process_in_background=true by default; returns file id immediately while extraction+embedding run async. Poll GET /api/v1/files/{id}/process/status (pending/completed/failed; stream=true for SSE). Adding a still-processing file to a KB fails silently or 400s — the pusher process MUST wait for 'completed'.
- OpenWebUI knowledge routes (verified in backend/open_webui/routers/knowledge.py, mounted at /api/v1/knowledge): POST /create; GET /, /{id}, /{id}/files, /{id}/files/pending; POST /{id}/update, /{id}/file/add {file_id} (calls process_file() and embeds into the collection at add time), /{id}/file/update (deletes old vectors then re-extracts+re-embeds — this is the per-article refresh primitive), /{id}/file/remove, /{id}/files/batch/add, /{id}/sync/diff, /{id}/sync/cleanup, /{id}/reset (clear all files); DELETE /{id}/delete; POST /reindex (admin, rebuilds all KBs). Also POST /api/v1/retrieval/process/web ingests a URL directly into a collection (overwrite=true replaces existing vectors).
- OpenWebUI KB use in chat: POST /api/chat/completions with body field files:[{"type":"collection","id":"<kb-id>"}] (or type:file). Direct text push: no dedicated raw-text endpoint — write text to a temp file and upload, or use /retrieval/process/web for URLs.
- OpenWebUI licensing (matters because the plan says 'refactored/integrated OpenWebUI'): v0.6.6+ is BSD-3 plus a branding-protection clause — 'Open WebUI' name/logo must stay visible and un-co-branded UNLESS the deployment has <=50 users in a rolling 30 days (Kade's single-user desktop app qualifies for branding removal) or an enterprise license. Code through v0.6.5 remains pure BSD-3.
- OpenWebUI MCP: native MCP support since v0.6.31 is Streamable HTTP ONLY; stdio/SSE MCP servers need the mcpo proxy (translates MCP to OpenAPI). So the platform's MCP server should expose streamable HTTP — one server can then serve both OpenWebUI tool-calling and Claude Code.
- Vector store versions/licenses (all verified on PyPI/GitHub 2026-08-01): chromadb 1.5.9 (Apache-2.0, Py>=3.9), lancedb 0.36.0 (Apache-2.0, Py>=3.10, Rust core, in-process/embedded, disk-based Lance columnar format), pgvector 0.8.6 (2026-07-29, PostgreSQL-license, requires a running PostgreSQL server).
- LanceDB has native BM25 full-text search and can route str queries to FTS and vector queries to ANN, enabling hybrid search with reranking. Caveats: FTS query strings don't support AND/OR operators; phrase queries need with_position=True at index build (bigger index); newly inserted rows aren't FTS-indexed until table.optimize() is called (until then they're covered by slower flat scans).
- Extraction libraries (PyPI, 2026-08-01): trafilatura 2.2.0 (released 2026-07-31, Apache-2.0 — it relicensed from GPLv3 at v1.8.0, so no copyleft concern, Py>=3.10); newspaper4k 0.9.6 (MIT, Py 3.10+, adds article discovery/crawling and NLP extras like keywords/summarization, 80+ languages).
- Chunking reality check for Alpaca/Benzinga news: articles are short — headline+summary is typically <200 tokens; with include_content=true the HTML body is usually a few hundred to ~1500 tokens. One-chunk-per-article (headline + summary + boilerplate-stripped content) works for most; split only bodies >~800 tokens and prepend the headline + symbols + date to every chunk so retrieval keeps context. Alpaca's stable id + updated_at give free dedup/refresh keys: upsert by id, re-embed only when updated_at changes; cross-source dedup by canonical URL or content hash.

Risks / constraints:
- Alpaca News API is still labeled v1beta1 and was 'free during beta' with plan-tied rate limits — pricing/terms could change; the spec should not hard-depend on wildcard websocket news remaining free.
- Alpaca free (non-realtime) market-data plans see 15-minute-delayed data on some endpoints; docs hint the same gating can apply to news defaults — the requirements doc should mandate an integration test that confirms the websocket delivers real-time news on Kade's key tier.
- OpenWebUI file processing is asynchronous: pushing a file into a knowledge collection before /process/status returns 'completed' fails silently or 400s. The pusher must poll (or use stream=true SSE) — a naive upload-then-add loop will silently produce an empty KB.
- OpenWebUI license (v0.6.6+) forbids removing/co-branding 'Open WebUI' branding above 50 users/30 days. A single-user desktop app is exempt, but if the platform is ever distributed to >50 users the refactored UI must keep branding or buy an enterprise license; forking from v0.6.5 (pure BSD-3) is the escape hatch at the cost of ~15 months of features.
- OpenWebUI's Knowledge/RAG internals (chunking, embedding model, vector backend) are its own and change between releases (v0.11.0 just reworked KB file search and access control); pinning an OpenWebUI version in requirements is essential since the platform integrates it rather than using it at arm's length.
- OpenWebUI native MCP is streamable-HTTP only — an stdio MCP server (the default for Claude Code usage) will NOT connect directly; either run the server as streamable HTTP from the start or accept running mcpo as a bridge.
- LanceDB FTS gotchas: no AND/OR in query strings, phrase search requires with_position=True (larger index), and new rows need optimize() before they hit the FTS index — the ingester needs a compaction timer or fresh articles will only match via slower flat scans.
- Benzinga content field is not guaranteed (contentless articles exist) and full-article extraction of third-party URLs (trafilatura) can hit paywalls, robots.txt restrictions, and publisher ToS — summarization of extracted text is fine for personal use but redistribution of article text inside a multi-user product is a copyright exposure.
- newspaper3k is abandoned — anything found in older tutorials should map to newspaper4k (MIT) or trafilatura; trafilatura versions before 1.8.0 were GPLv3, so pin >=2.0 to stay Apache-2.0.
- pgvector 0.8.6 would require bundling and servicing a full PostgreSQL instance inside the Windows-exe install — operationally the worst fit of the three stores for a desktop app; only reconsider it if OpenWebUI's own store is switched to pgvector for large-KB hybrid-search performance (a v0.10.0 optimization) and one shared Postgres is desired.

## Completeness critique

The 12 reports are strong inside their silos — versions, licenses, and API capabilities are genuinely verified with primary sources, and the license landscape (OpenWebUI branding clause with the <=50-user exemption, LWC Apache+attribution, AGPL open-webui/desktop avoidance, TradingView Advanced Charts rejection) is consistent across all reports that touch it. The document-killing weaknesses are all in the seams: nobody owns the cross-broker abstraction (unified order model, symbology, capability matrix, error taxonomy), nobody sources historical data for the futures/SPX instruments only tastytrade can trade, and nobody wrote the AI-trading-guardrails section a platform that lets an LLM place orders cannot ship without. Three genuine cross-researcher contradictions must be adjudicated before drafting: MCP transport (resolve to Streamable HTTP), vector store (LanceDB vs sqlite-vec/numpy — scope per subsystem), and the Claude billing model — which my direct check resolved: the Agent SDK credit program is paused and subscription-authenticated Agent SDK usage draws from normal plan limits (supported), while reusing CLAUDE_CODE_OAUTH_TOKEN in OWUI or other harnesses is a ToS violation enforced server-side — so the platform's AI loop should be Agent SDK + subscription, with a metered API key only for optional OWUI-native chat. With those three decisions made and the ~11 gaps assigned as sections or tracked open issues (Webull key lifetime, Fidelity/SnapTrade specifics, py-vollib-vectorized-on-3.12 test), the research base is sufficient to draft the requirements document."

Gaps to close during build:
- CROSS-BROKER ABSTRACTION LAYER (biggest gap): no researcher designed the unified layer the platform actually rests on — a normalized order/position/execution model across Alpaca REST + tastytrade + Webull; a unified symbology map (OCC option symbols vs tastytrade instrument symbols vs dxFeed streamer symbols vs Webull instrument_type/legs); a normalized order-state machine reconciling Alpaca trade_updates events vs tastytrade full-object account-streamer messages vs Webull gRPC order events; and a per-broker x asset x order-type capability matrix (bracket/OCO = Alpaca equities only; OTOCO/OCO = tastytrade separate complex-order endpoints with separate IDs; 4-leg cap both brokers but different rules; naked short options = tastytrade only, never Alpaca; fractional = market-only on Alpaca). Without this matrix the UI cannot gate controls per broker and orders will be rejected. A builder hits this in week 1.
- HISTORICAL DATA FOR TASTYTRADE-ONLY INSTRUMENTS: tastytrade supports futures, futures options, and SPX live, but has no deep REST OHLC history (DXLink Candle replay only, ~1 day of 1-min practical), and Alpaca — the designated 'bulk history elsewhere' fallback — carries NO futures and NO index (SPX/VIX) data at all. Charting /ES or SPX with real history has no identified source anywhere in the 12 reports. Requirements must either name a supplemental data vendor (e.g. Polygon indices, Databento CME) with cost, or explicitly descope futures/index charting.
- AI TRADING GUARDRAILS: an MCP server exposing order placement to an LLM appears in three reports, yet no report specifies a human-confirmation gate before AI-initiated orders, position/notional size limits, a kill switch, dry-run-first policy, or audit logging (claude-mcp correctly notes MCP has no built-in audit trail, but no one proposes the app-level logging design). For a trading platform this is a mandatory requirements section, currently absent.
- MID-PRICE SOURCE OF TRUTH: Kade's standing rule is mid fills on every options view, but the same contract will show different mids per feed — Alpaca free tier serves indicative (non-OPRA) options quotes while tastytrade DXLink serves real quotes; no report defines which feed prices which instrument, how cross-broker positions in one portfolio view are marked, or how P&L/cost-basis is computed across brokers (no researcher covered portfolio aggregation or realized/unrealized P&L accounting at all).
- REGULATORY/ACCOUNT MECHANICS: zero coverage of PDT day-trade counting (margin accounts under $25k), margin-call display, options assignment/exercise workflows (beyond Alpaca's auto-exercise note), corporate actions, or Section 1256 handling beyond a mention — at minimum PDT-aware order gating belongs in requirements.
- PAPER/LIVE MODE AS A PLATFORM CONCEPT: sim fidelity differs radically per broker (Alpaca paper = good but optimistic fills; tastytrade cert = 15-min delayed quotes, $1 market fills, 24h resets, no market metrics; Webull sandbox = shared test accounts) and Fidelity has nothing. No report defines a global paper/live toggle UX or states that 'paper mode' cannot exist uniformly across brokers.
